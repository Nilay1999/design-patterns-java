# Machine Coding — In-Memory SQL Database (with Indexing)

> **What this round is:** A 90–120 min *machine-coding / LLD* round (Razorpay, Flipkart, Atlassian style). They want **working, runnable code** with clean OOP, good naming, and an API you can *extend live* when they add follow-ups. It is **not** a distributed-systems whiteboard round — don't talk about sharding or Raft. Talk about classes, interfaces, and data structures.
>
> **How they grade:** (1) Did it run and pass their scenarios? (2) Is the design extensible — can you add an index / transaction without rewriting? (3) Did you reason about trade-offs out loud? (4) Clean code: separation of concerns, no god-class.

---

## 1. How to drive the first 10 minutes

Don't start coding. Say this out loud and write the scope on the board:

1. **Clarify scope** — "I'll support `CREATE TABLE`, `INSERT`, `SELECT … WHERE`, `UPDATE`, `DELETE`, and secondary `INDEX`es. I'll parse a small struct-based API, not raw SQL strings — is that ok?" (99% yes. Parsing real SQL is a time-sink trap.)
2. **State the headline feature** — indexing: "Equality lookups go through a hash index; range queries through a sorted index. Without an index I fall back to a full table scan. I'll show a query planner that picks the index."
3. **Name the data structures before writing them** — `HashMap<Object, Set<Long>>` (value → row ids) for equality, `TreeMap` for ranges. This one sentence is what separates a senior from a junior in this round.
4. **Defer the hard stuff explicitly** — "Transactions, composite indexes, and a SQL parser are natural extensions; I'll build the core first and we can layer those if there's time." Interviewers love hearing the extension path stated early.

---

## 2. Requirements

**Functional**
- Create a table with a typed schema and a primary key.
- `INSERT` a row (auto-assign PK if not given).
- `SELECT` with zero or more `WHERE` conditions (`=, !=, <, <=, >, >=`), projection of columns.
- `UPDATE` / `DELETE` rows matching conditions.
- Create a **secondary index** on a column; queries must use it automatically.

**Non-functional (call these out)**
- Lookups by indexed column → **O(1)** (equality) / **O(log n + k)** (range).
- Indexes must stay **consistent** on every insert/update/delete — this is the bug they're hunting for.
- Extensible to composite indexes and transactions.

---

## 3. Build it in tiers (this is the real skill)

**Do not write the whole thing at once.** The way you pass this round is by always having something that runs. Build in three tiers and tell the interviewer you're doing it:

- **Tier 1 — working DB, no index (~30–40 min).** Full-scan CRUD. ~40 lines. This *alone* is a passing baseline. Demo it before touching indexing.
- **Tier 2 — equality index + planner (~20 min).** The headline. Genuinely O(1) lookups, ~15 lines. This is where most of the credit is.
- **Tier 3 — range index (only if time).** A `TreeMap`-backed `SortedIndex`. Do **not** hand-roll binary search under a clock.

The full monolithic "B-tree-grade" engine is not the bar. A clean Tier 1 + Tier 2 with the trade-offs spoken out loud beats a half-finished fancy version every time.

```
Database ── Map<String, Table>
Table    ── rows + (Tier 2) indexes + CRUD + createIndex
Index    ── interface { add, remove, find }   ← Tier 2 (strategy pattern)
QueryPlanner ── pick an index, else full scan ← Tier 2
```

## 4. Tier 1 — working DB, no index

The whole point: get a correct, runnable CRUD engine fast. A `WHERE` is just an array of predicates ANDed together; `select` is a `filter`.

```java
enum Op { EQ, NE, LT, LTE, GT, GTE }

// a WHERE predicate: column <op> value
record Condition(String column, Op op, Object value) {}

class Predicates {
  @SuppressWarnings("unchecked")
  static boolean matches(Map<String, Object> row, Condition c) {
    Object v = row.get(c.column());
    if (c.op() == Op.EQ) return Objects.equals(v, c.value());
    if (c.op() == Op.NE) return !Objects.equals(v, c.value());
    int cmp = ((Comparable<Object>) v).compareTo(c.value()); // <, <=, >, >=
    return switch (c.op()) {
      case LT -> cmp < 0;  case LTE -> cmp <= 0;
      case GT -> cmp > 0;  case GTE -> cmp >= 0;
      default -> false;
    };
  }

  static boolean allMatch(Map<String, Object> row, List<Condition> conditions) {
    for (Condition c : conditions) if (!matches(row, c)) return false;
    return true;
  }
}

class Table {
  // LinkedHashMap keeps insertion order → predictable scans. A row is just a map.
  protected final Map<Long, Map<String, Object>> rows = new LinkedHashMap<>();
  private long nextId = 1;

  Map<String, Object> insert(Map<String, Object> row) {
    long id = nextId++;
    Map<String, Object> stored = new HashMap<>(row);
    stored.put("id", id);
    rows.put(id, stored);
    return stored;
  }

  List<Map<String, Object>> select(List<Condition> conditions) {
    List<Map<String, Object>> out = new ArrayList<>();
    for (Map<String, Object> r : rows.values())
      if (Predicates.allMatch(r, conditions)) out.add(r);
    return out;
  }

  int update(List<Condition> conditions, Map<String, Object> changes) {
    int n = 0;
    for (Map<String, Object> r : rows.values())
      if (Predicates.allMatch(r, conditions)) { r.putAll(changes); n++; }
    return n;
  }

  int delete(List<Condition> conditions) {
    int n = 0;
    for (Iterator<Map<String, Object>> it = rows.values().iterator(); it.hasNext(); )
      if (Predicates.allMatch(it.next(), conditions)) { it.remove(); n++; }
    return n;
  }
}
```

That's a working database. Run a demo, *then* say: "Now `select` is O(n) — let me add an index so equality lookups are O(1)."

## 5. Tier 2 — the headline: an equality index

This is what the question is actually testing. One `Index` interface (so it's pluggable), one `HashIndex`, and a planner that uses it. ~30 lines total.

```java
interface Index {
  void add(Object value, long id);
  void remove(Object value, long id);
  Set<Long> find(Op op, Object value); // null = "can't serve this op" → planner falls back
}

// O(1) equality lookups. Backs `col = x`.
class HashIndex implements Index {
  private final Map<Object, Set<Long>> map = new HashMap<>();

  public void add(Object value, long id) {
    map.computeIfAbsent(value, k -> new HashSet<>()).add(id);
  }
  public void remove(Object value, long id) {
    Set<Long> ids = map.get(value);
    if (ids != null) ids.remove(id);
  }
  public Set<Long> find(Op op, Object value) {
    return op == Op.EQ ? new HashSet<>(map.getOrDefault(value, Set.of())) : null;
  }
}
```

Give `Table` an `indexes` map and keep it in sync on every write — **this consistency is the bug they hunt for** (§7). In the round you'd put this directly in `Table`; shown as a subclass only to highlight what Tier 2 *adds*:

```java
class IndexedTable extends Table {
  private final Map<String, Index> indexes = new HashMap<>();

  void createIndex(String column) {
    Index index = new HashIndex();
    for (Map<String, Object> row : rows.values())          // back-fill existing rows!
      index.add(row.get(column), (Long) row.get("id"));
    indexes.put(column, index);
  }

  // override insert/update/delete to maintain `indexes`, then use the planner in select():
  @Override
  List<Map<String, Object>> select(List<Condition> conditions) {
    Set<Long> candidates = QueryPlanner.plan(conditions, indexes);
    Collection<Map<String, Object>> scan =
        candidates == null ? rows.values()                  // no usable index → full scan
                           : candidates.stream().map(rows::get).toList();
    List<Map<String, Object>> out = new ArrayList<>();
    for (Map<String, Object> r : scan)
      if (r != null && Predicates.allMatch(r, conditions)) out.add(r);
    return out;
  }
}
```

```java
class QueryPlanner {
  // candidate id-set if any condition hits an index, else null (→ full scan)
  static Set<Long> plan(List<Condition> conditions, Map<String, Index> indexes) {
    for (Condition c : conditions) {
      Index index = indexes.get(c.column());
      if (index != null) {
        Set<Long> ids = index.find(c.op(), c.value());
        if (ids != null) return ids;
      }
    }
    return null;
  }
}
```

**Say this out loud:** `WHERE age = 30 AND city = 'NYC'` → planner finds the `age` index → `find(EQ, 30)` returns a handful of ids in O(1) → filter those by `city`. No full scan. *That's the whole point of the round.*

## 6. Tier 3 — range queries (only if time)

**Don't hand-roll binary search.** Java's `TreeMap` (a red-black tree) gives you sorted keys and O(log n) range slices for free — `headMap`/`tailMap`/`subMap`. The whole range index is ~15 lines and shares the `Index` interface, so the planner picks it up with zero changes:

```java
class SortedIndex implements Index {
  private final NavigableMap<Object, Set<Long>> map = new TreeMap<>();

  public void add(Object value, long id) {
    map.computeIfAbsent(value, k -> new HashSet<>()).add(id);
  }
  public void remove(Object value, long id) {
    Set<Long> ids = map.get(value);
    if (ids != null) { ids.remove(id); if (ids.isEmpty()) map.remove(value); }
  }
  public Set<Long> find(Op op, Object value) {
    // O(log n) to locate the boundary, then walk the matching sub-map
    SortedMap<Object, Set<Long>> sub = switch (op) {
      case EQ  -> map.subMap(value, true, value, true);
      case LT  -> map.headMap(value, false);
      case LTE -> map.headMap(value, true);
      case GT  -> map.tailMap(value, false);
      case GTE -> map.tailMap(value, true);
      default  -> null; // NE → not worth an index, let the planner fall back to scan
    };
    if (sub == null) return null;
    Set<Long> out = new HashSet<>();
    for (Set<Long> ids : sub.values()) out.addAll(ids);
    return out;
  }
}
```

`createIndex` just instantiates a `SortedIndex` instead of a `HashIndex` for columns you'll range-query. *That* extensibility — a new index type dropping in behind the same interface — is the point you're demonstrating.

## 7. The bug they're hunting: index consistency

The #1 thing that fails this round is an index that drifts out of sync with the data. Three rules — recite them:

1. **INSERT** → add to every index.
2. **DELETE** → remove from every index *before* dropping the row (you still need the old values).
3. **UPDATE** → `remove(oldValue)` → mutate → `add(newValue)`, but only for columns that actually changed.

Also: **`createIndex` must back-fill existing rows** (see code). Building an empty index on a populated table is the classic silent bug.

## 8. Follow-ups they will pile on (and the answer)

| Follow-up | What to say / do |
|---|---|
| **Composite index** `(a, b)` | Key the index on a tuple/encoded string `${a} ${b}`. Honors the **leftmost-prefix rule** (see `2.database-fundamentals.md`): serves `a=` and `a=,b=`, not `b=` alone. |
| **Query optimizer / multiple indexes** | Track each index's cardinality; pick the **most selective** one (smallest candidate set), or **intersect** id-sets from several indexes. |
| **Transactions (ACID)** | Keep an **undo log**: on `begin`, record inverse ops; `commit` clears it, `rollback` replays inverses (incl. index fixes). Or snapshot via copy-on-write. Mention isolation levels but don't build MVCC unless asked. |
| **Concurrency** | A single `ReentrantReadWriteLock` per table is the honest, simple answer (`ConcurrentHashMap` for the store); row-level locking if pushed. |
| **`ORDER BY` / `LIMIT`** | A `SortedIndex` already yields keys in order — return ids in index order and slice for `LIMIT`. |
| **`JOIN`** | Index-nested-loop join: scan left table, probe the right table's index on the join key. |
| **Persistence** | Append-only **write-ahead log** of operations; replay on startup. Rebuild indexes from data on load. |
| **Real SQL string parsing** | Tokenize → small recursive-descent parser → produce the same `List<Condition>`. Offer it last; it's pure plumbing, not what they're testing. |

## 9. Java gotchas to mention (so the interviewer knows you know)

- **`Objects.equals` for `EQ`/`NE`, `Comparable.compareTo` for ranges.** Don't use `==` on boxed values — `Long.valueOf(128) == Long.valueOf(128)` is `false` (outside the −128..127 cache). This is the classic bug.
- **Heterogeneous values → `Object` + cast to `Comparable`.** `((Comparable<Object>) v).compareTo(...)` works for `Integer`, `String`, etc. Acknowledge it throws if a column mixes types — fine for the exercise.
- **`computeIfAbsent`** keeps the index add path to one line and avoids the get-null-then-put race.
- **`LinkedHashMap`** for the row store gives deterministic scan order, which makes your demo output stable.
- **`TreeMap` is the whole range story** — `headMap`/`tailMap`/`subMap` return live, O(log n)-located sub-views. No manual binary search, ever.
