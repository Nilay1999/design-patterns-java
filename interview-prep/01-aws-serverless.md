## 1. EventBridge

### What it is

EventBridge is a serverless **event bus**. A service publishes an event onto the bus using the `PutEvents` API. The bus then looks at every **rule** attached to it. A rule contains a pattern. If the event matches the pattern, EventBridge delivers a copy of the event to that rule's **targets**.

The important part is that the publisher does not know who the consumers are. It publishes "a shipment was created" and walks away. If you later want a second team to react to that same event, they add their own rule. The publisher does not change, does not redeploy, and does not even find out. That is the real reason to use a bus instead of calling another service directly.

EventBridge is a **push** system. You do not poll it. It calls your target for you.

### The event envelope, field by field

Every event on the bus has the same shape:

```json
{
  "version": "0",
  "id": "uuid",
  "detail-type": "ShipmentCreated",
  "source": "com.elevation.ingestion",
  "account": "123456789012",
  "time": "2026-08-06T10:00:00Z",
  "region": "us-east-1",
  "resources": [],
  "detail": { "shipmentId": "S-1", "orderId": "O-9", "s3Key": "raw/2026/08/06/S-1.xml" }
}
```

| Field | Who sets it | What it means and how to use it |
|---|---|---|
| `version` | AWS | Envelope schema version. Always `"0"` today. You never touch it. |
| `id` | AWS | A unique identifier for this event, generated by EventBridge. This is a good natural idempotency key for consumers, but be careful: a replayed event gets a new delivery, so pair it with a business key if you use replay. |
| `detail-type` | You | The name of the event, for example `ShipmentCreated`. This is your first routing dimension. Treat it like a class name: a noun plus a past-tense verb. |
| `source` | You | Who published the event, for example `com.elevation.ingestion`. This is your second routing dimension. Use reverse-domain naming so that AWS-generated sources (which always start with `aws.`) never collide with yours. |
| `account` | AWS | The AWS account that published the event. Useful when several accounts publish to one central bus. |
| `time` | You or AWS | The event time. If you do not set it, EventBridge sets it to the time it received the event. Set it yourself when the event describes something that happened earlier, otherwise your ordering and audit trail become misleading. |
| `region` | AWS | Where the event was published. |
| `resources` | You | An optional list of ARNs the event relates to. AWS service events fill this in. Most teams leave it empty for custom events. |
| `detail` | You | Your payload. Must be valid JSON. This is where the business data lives. |

**Designing `source` and `detail-type` well matters more than it looks.** These two fields are how every future consumer will find your events. Think of them as a topic taxonomy that you will be stuck with for years. A good scheme is `source = com.<company>.<bounded-context>` and `detail-type = <Entity><PastTenseVerb>`.

**Payload must be JSON.** If your incoming data is XML, or a five megabyte document, you do not put it in `detail`. You write the raw file to S3 and put the S3 key in `detail`. The consumer reads the file from S3 when it needs it. This is called the **claim-check pattern**, and it is the standard answer for "your payload is bigger than the limit."

### Rules and event patterns, explained

A rule has three parts: an event pattern (what to match), a list of targets (where to send it), and optional input transformation (how to reshape it before sending).

The pattern is matched against the **structure** of the JSON, not as text. You write a pattern that mirrors the shape of the event, and the value at each leaf is an array of things that are allowed there.

```json
{
  "source": ["com.elevation.ingestion"],
  "detail-type": ["ShipmentCreated", "ShipmentUpdated"],
  "detail": {
    "region": ["us-east", "us-west"],
    "quantity": [{ "numeric": [">", 0] }],
    "sku": [{ "prefix": "SKU-" }],
    "status": [{ "anything-but": ["DRAFT"] }],
    "customerId": [{ "exists": true }]
  }
}
```

Rules for reading this:

- A field listed in the pattern **must be present and must match**, unless you use `exists: false`.
- A field **not** listed in the pattern is ignored completely. So a pattern of `{"source": ["x"]}` matches every event from source `x`, whatever else is inside it.
- Values in an array are combined with **or**. Different fields are combined with **and**.
- If the event field is itself an array, the rule matches when **any** element of that array matches.

The comparators you can use:

| Comparator | Example | What it does |
|---|---|---|
| Exact value | `["ACTIVE"]` | Matches the exact string or number. |
| `prefix` | `[{"prefix": "SKU-"}]` | Matches strings starting with the text. |
| `suffix` | `[{"suffix": ".xml"}]` | Matches strings ending with the text. |
| `anything-but` | `[{"anything-but": ["DRAFT"]}]` | Matches anything except the listed values. Can take a list, a prefix, or a number. |
| `numeric` | `[{"numeric": [">", 0, "<=", 100]}]` | Numeric comparison. You can chain two bounds in one expression. |
| `exists` | `[{"exists": true}]` | Field must be present (or must be absent with `false`). |
| `cidr` | `[{"cidr": "10.0.0.0/8"}]` | IP address falls inside a network range. |
| `equals-ignore-case` | `[{"equals-ignore-case": "active"}]` | Case-insensitive exact match. |
| `wildcard` | `[{"wildcard": "raw/*/partnerA/*"}]` | Simple star matching inside a string. |
| `$or` | `{"$or": [ {...}, {...} ]}` | Combines two whole sub-patterns with or. |

**Why filter at the bus instead of in your code?** Because an event that does not match never invokes your target. You do not pay for the Lambda invocation, you do not burn concurrency, and you do not have to write and test the "not for me, return early" branch. Filtering at the bus is both cheaper and simpler than filtering in the consumer.

### Input transformation

Before delivering to a target, a rule can reshape the event. You define an **input path map** (pull out pieces of the event into named variables) and an **input template** (a string or JSON built from those variables). This is how you send a plain text line to a Slack webhook, or a small trimmed object to a Lambda that does not need the whole envelope. It saves writing a small Lambda purely to reformat data.

### Bus types

| Bus type | What goes on it | When you use it |
|---|---|---|
| **Default bus** | Every AWS service event in the account lands here automatically: EC2 state changes, ECS task state changes, CodePipeline stages, S3 events when EventBridge notifications are on, and anything routed through CloudTrail. | Reacting to infrastructure and AWS-managed events. Do not publish your own domain events here; they will be lost in the noise. |
| **Custom bus** | Only what you publish. | Your domain events. Best practice is one bus per bounded context, and always separate buses per environment. Never let a non-production event reach a production bus. |
| **Partner bus** | A software-as-a-service vendor pushes directly: Stripe, Datadog, Auth0, Shopify, and others. | Receiving third-party webhooks without running a webhook endpoint, and without managing signature checks and retries yourself. |

### Delivery guarantees — say this precisely in an interview

- Delivery is **at-least-once**. Duplicates are possible. Your consumers must be idempotent. There is no configuration that turns this off.
- Delivery is **asynchronous** and there is **no ordering guarantee**. Two events published one after the other can arrive in the opposite order. If order matters, EventBridge is the wrong tool by itself; put a FIFO queue or Kinesis stream in the path, or carry a version number in the event and ignore older versions.
- If a target fails, EventBridge retries with exponential backoff for up to **24 hours**.
- Each target can have its own **dead letter queue**, which is an SQS queue. Events that exhaust retries, or that can never be delivered (target deleted, permissions removed, target throttling permanently), land there instead of vanishing. Configure this on every target. An event that silently disappears is the worst failure mode in an event-driven system.

### Archive and replay

An **archive** stores a copy of every event that matches a chosen pattern, for a retention period you set (a number of days, or indefinitely). A **replay** takes a time window from that archive and re-publishes those events onto the bus, delivered only to the rules you select.

This is the answer to "a bug corrupted a day of data, how do you reprocess it?" You fix the consumer, then replay yesterday between 09:00 and 17:00 into a rule that points only at the fixed consumer.

Two things to know:

- Replayed events carry a replay marker in the envelope, so a consumer can tell it is seeing a replay.
- Replay does not remove the need for idempotency. In fact replay is exactly the situation where a non-idempotent consumer causes double charges and duplicate rows.

### Schema Registry

The Schema Registry watches traffic on a bus, infers the JSON Schema or OpenAPI shape of the events flowing through it, versions those schemas, and can generate typed code bindings for Java, Python, and TypeScript.

Be precise about what it does **not** do: it does not reject an event that fails a schema. EventBridge will happily deliver a malformed event. The registry is a discovery and versioning tool, plus a code-generation convenience. Actual enforcement has to happen in your producer (validate before publishing) or your consumer (validate on receipt and route failures to a rejects queue).

### EventBridge Bus, Pipes, and Scheduler — three different products

| Product | Shape | What it replaces |
|---|---|---|
| **Bus** | One source, many rules, many targets. Content-based routing and fan-out. | A service calling five other services directly. |
| **Pipes** | Point to point. One source, optional filter, optional enrichment, one target. Pipes does the polling for you against SQS, Kinesis, DynamoDB Streams, Amazon MQ, and MSK. | The Lambda whose only job was "read from queue, reshape, write somewhere else." |
| **Scheduler** | Cron, rate, or one-time schedules. Handles millions of individual schedules, each with its own target and payload. | CloudWatch Events scheduled rules, and homegrown "table of things to do later plus a polling Lambda." |

Scheduler is genuinely useful and under-used. If your product needs "send a reminder 24 hours before the booking", you create one schedule per booking rather than scanning a table every minute.

### Limits worth knowing

| Limit | Value | What it means for you |
|---|---|---|
| Event size | 256 KB | Same as SQS. Larger payloads go to S3, event carries the key. |
| `PutEvents` batch | 10 entries per call | Batch your publishes. A partial failure is reported per entry, so check the response and retry only the failed entries. |
| `PutEvents` throughput | Thousands per second by default, region dependent, raisable on request | Publishing is rarely your bottleneck. Target invocation limits usually bite first. |
| Targets per rule | 5 | If you need more than five consumers, either use more rules with the same pattern, or fan out to SNS. |
| Rules per bus | A few hundred by default, raisable | Fine for domain events. Not fine for "one rule per customer" designs — use Scheduler or a routing table instead. |

### How EventBridge scales

**What scales automatically:** the bus itself, the rule evaluation, and the delivery. You do not provision anything. There are no shards, no partitions, and no capacity units. Publishing throughput is a soft account limit you raise with a support ticket.

**What actually limits you:** the target. If a rule points at a Lambda and 20,000 events arrive in one second, EventBridge tries to invoke that Lambda 20,000 times. The Lambda hits its concurrency limit, throttles, and EventBridge starts retrying. Your bus is fine; your consumer is on fire.

**How you fix that:** put an SQS queue between the rule and the Lambda. The rule delivers into the queue at whatever rate events arrive, and the Lambda drains the queue at whatever rate it can handle. The queue absorbs the spike. This is the single most important scaling pattern in EventBridge architectures, and interviewers look for it.

**Other scaling notes:**

- Filter at the rule, not in code. A pattern that rejects 90 percent of events reduces your consumer load by 90 percent for free.
- `ThrottledRules` in CloudWatch tells you the bus is limiting rule invocations. `FailedInvocations` tells you targets are rejecting deliveries. Alarm on both.
- Fan-out costs multiply. One event matching five rules is five deliveries and five downstream invocations. Model this before you assume the bill is small.

### EventBridge compared with SNS, SQS, and Kinesis

| | EventBridge | SNS | SQS | Kinesis |
|---|---|---|---|---|
| Model | Bus with content routing | Publish and subscribe topic | Queue, point to point | Ordered log or stream |
| Consumers | Rules leading to targets | Subscribers | One logical consumer group per queue | Many, each with its own position |
| Filtering | Rich, on the whole payload | Attribute and payload filter policies | Not available | Not available, filter in consumer |
| Ordering | None | FIFO topic option | FIFO queue option | Guaranteed per partition key |
| Replay | Archive and replay | No | Only dead letter queue redrive | Yes, within the retention window |
| Latency | Roughly sub-second, more variable | Lowest | Low | Low |
| Throughput | High | Very high | Effectively unlimited on standard queues | Set by shard count |
| Scaling model | Fully automatic | Fully automatic | Fully automatic | You provision shards, or use on-demand |
| Best for | Routing domain events between services | Broad fan-out notifications | Buffering work and distributing it | High-volume ordered analytics and change data capture |

**Interview answer for "why EventBridge and not SNS?"** — EventBridge gives content-based routing over the entire payload rather than only message attributes, archive and replay for audit and reprocessing, a large set of native targets so you do not write glue code, and a schema registry. SNS wins when you want the lowest latency, the highest raw throughput, or FIFO ordering with fan-out. SQS is not really the competitor to either; it is the buffer you place **behind** one of them so that each consumer can fail and retry on its own without affecting the others.

## 2. SQS

### What it is

SQS is a fully managed queue. Producers send messages, consumers poll for messages, process them, and then delete them. The delete is the acknowledgement. If a consumer never deletes a message, the message comes back and someone else gets it.

The value of a queue is not transport, it is **decoupling in time**. The producer can run at 10,000 messages per second while the consumer runs at 500 per second, and nothing breaks — the backlog simply grows and then drains. A queue turns a traffic spike into a delay instead of an outage.

### Queue types

| | Standard queue | FIFO queue |
|---|---|---|
| Throughput | Effectively unlimited | 300 transactions per second per API action, 3,000 with batching. High-throughput FIFO mode raises this to tens of thousands. |
| Ordering | Best effort. Usually in order, no guarantee. | Strict order **within a message group**. |
| Delivery | At-least-once. Duplicates possible. | Exactly-once **processing** within a 5-minute deduplication window. |
| Name | Anything | Must end in `.fifo` |
| When to use | Almost always. Default choice. | Only when order genuinely matters for correctness. |

**The FIFO detail people get wrong:** ordering is per `MessageGroupId`, not per queue. If every message uses the same group id, you get a single-threaded consumer and terrible throughput. If you use `storeId` or `orderId` as the group id, you get strict ordering within each store or order **and** full parallelism across stores or orders. Choosing the group id well is the whole design decision.

### Every SQS property explained

| Property | Default | Range | What it does and how to choose |
|---|---|---|---|
| **Visibility timeout** | 30 seconds | 0 seconds to 12 hours | When a consumer receives a message, the message becomes invisible to everyone else for this long. If the consumer deletes it in time, it is gone. If not, it becomes visible again and another consumer picks it up — which means duplicate processing. **Set it to at least your worst-case processing time.** For Lambda consumers, AWS recommends roughly six times the function timeout. For long jobs, call `ChangeMessageVisibility` periodically as a heartbeat to extend it while you work. |
| **Message retention period** | 4 days | 1 minute to 14 days | How long an undelivered message survives. After this it is deleted permanently, with no notification. Set dead letter queues to the maximum 14 days so you have time to notice and fix. |
| **Delivery delay** | 0 seconds | 0 to 15 minutes | Every message sent to the queue stays invisible for this long before anyone can receive it. Set per queue, or per message with a message timer. A cheap first-tier retry backoff: on failure, re-send the message with a delay instead of letting it retry immediately. |
| **Maximum message size** | 256 KB | 1 KB to 256 KB | Bigger payloads use the SQS Extended Client Library, which writes the body to S3 and puts a pointer in the message. Again the claim-check pattern. |
| **Receive message wait time** (long polling) | 0 seconds (short polling) | 0 to 20 seconds | With 0, a receive call returns immediately even if the queue is empty, so you burn API calls and money spinning. With 20, the call waits up to 20 seconds for a message to arrive and returns as soon as one does. **Always set this to 20.** It reduces cost, reduces empty responses, and actually lowers latency compared with a tight polling loop. |
| **Content-based deduplication** (FIFO only) | Off | On or off | When on, SQS hashes the message body to produce the deduplication id automatically. When off, you supply `MessageDeduplicationId` yourself. Either way, a repeated id within 5 minutes is silently discarded. |
| **Redrive policy** | None | — | Points at a dead letter queue and sets `maxReceiveCount`. After a message has been received that many times without being deleted, SQS moves it to the dead letter queue. Typical values are 3 to 5. Too low and a transient blip poisons good messages; too high and a bad message wastes a lot of compute before you find it. |
| **Redrive allow policy** | Allow all | — | Set on the dead letter queue, controls which source queues are allowed to use it. Prevents accidental sharing. |
| **Server-side encryption** | SSE-SQS | SSE-SQS or SSE-KMS | SSE-SQS is free and managed by AWS. SSE-KMS gives you your own key, an audit trail in CloudTrail, and per-key permissions, but it adds KMS API calls to every operation, which costs money and has its own throttling limits at high volume. |
| **Access policy** | Owner only | — | A resource policy on the queue. This is what you edit to let EventBridge, SNS, or another account send messages to your queue. |

### Dead letter queues and redrive, properly

A dead letter queue is just another SQS queue. Nothing special about it except how you use it.

The flow is: consumer fails to process → message becomes visible again after the visibility timeout → this repeats until the receive count reaches `maxReceiveCount` → SQS moves the message to the dead letter queue.

Then **dead letter queue redrive** lets you send those messages back to the source queue from the console or the API, once you have fixed the bug. You can redrive everything or a limited rate.

Always put a CloudWatch alarm on `ApproximateNumberOfMessagesVisible` for every dead letter queue, with a threshold of one. A dead letter queue nobody watches is a silent data-loss machine.

### Lambda plus SQS event source mapping — know this cold

When you attach an SQS queue to a Lambda, you are not "triggering" Lambda from SQS. The Lambda service runs a fleet of pollers that call `ReceiveMessage` on your behalf, and invokes your function with whatever they get.

| Setting | What it does |
|---|---|
| **Batch size** | How many messages arrive in one invocation. Up to 10 for standard queues with no batch window; up to 10,000 when you also set a batch window. Bigger batches mean fewer invocations and lower cost, but a longer processing time per invocation and a bigger blast radius on failure. |
| **Batch window** (`MaximumBatchingWindowInSeconds`) | Up to 300 seconds. The poller waits this long to fill the batch before invoking. Trades latency for efficiency. Use it for high-volume, latency-tolerant pipelines; leave it at 0 for latency-sensitive work. |
| **Report batch item failures** | The setting that matters most. When enabled, your function returns `{"batchItemFailures": [{"itemIdentifier": "<messageId>"}]}` and only those messages return to the queue. Without it, **one bad message forces the entire batch to be retried**, so nine good messages get processed twice, and your duplicate rate multiplies. Turn this on for every batched consumer. |
| **Maximum concurrency** (on the event source mapping) | Caps how many concurrent invocations this specific queue can drive, without reserving account concurrency. Newer and usually better than using reserved concurrency for this purpose. |
| **Filter criteria** | Event-pattern filtering on the message body, evaluated by the Lambda service before invoking. Messages that do not match are deleted, not returned. Be careful: filtered-out messages are discarded, not preserved. |

Successful messages are deleted by the Lambda service automatically. Failures go back to the queue and eventually to the dead letter queue.

### How SQS scales

**What scales automatically:** everything, on standard queues. There is no capacity to provision, no shards, no partitions. You can go from zero to a very high message rate with no configuration. SQS itself is essentially never your bottleneck.

**How consumer scaling works with Lambda:** the Lambda service starts with **5 concurrent pollers**. If the backlog keeps growing, it adds roughly **60 more concurrent invocations per minute**, up to 1,000 concurrent invocations for a standard queue (or up to your account limit if lower). For FIFO queues it scales up to the number of active message groups, because it cannot process two messages from one group at the same time.

The practical consequence is that **SQS-triggered Lambda ramps up over minutes, not instantly**. If a million messages land in one second, you do not get a million concurrent Lambdas. You get five, then sixty-five, then a hundred and twenty-five, and so on. Plan your latency expectations around that ramp, and pre-warm with provisioned concurrency if a spike must be absorbed quickly.

**The backpressure hazard you must mention in an interview:** an SQS-triggered Lambda will happily consume your **entire account concurrency** and starve every other function in the account, including your API-facing ones. Two fixes: set **maximum concurrency on the event source mapping** (preferred), or set **reserved concurrency** on the function. Reserved concurrency has the extra benefit of capping how many database connections the pipeline can open, which protects Aurora.

**The metric that tells you whether you are keeping up:** `ApproximateAgeOfOldestMessage`. Queue depth alone is misleading, because a deep queue that drains quickly is healthy and a shallow queue that never drains is not. Age of the oldest message is the true service-level indicator for a queue. Alarm on it.

**Scaling FIFO queues:** the base limit is 300 transactions per second per API action, or 3,000 with batches of 10. **High-throughput FIFO** raises this dramatically by relaxing deduplication scope from queue-level to message-group-level. If you need more throughput than that, the real fix is a better `MessageGroupId` that spreads load across more groups.

### Idempotency with SQS — the guaranteed follow-up question

Standard SQS delivers at-least-once, so duplicates will happen. There is no setting to fix this. You handle it in the consumer. Three approaches:

1. **Natural idempotency.** Write with `INSERT ... ON CONFLICT DO NOTHING` or `ON CONFLICT DO UPDATE`, keyed on a business identifier. The second copy of a message simply overwrites with the same values, or does nothing. This is the cheapest option and should be your first choice.
2. **A deduplication table.** A DynamoDB table with a time-to-live attribute, or a unique index in Aurora, keyed on `messageId` or a domain-level idempotency key. Write it with a conditional put, and skip processing if the write fails because the key already exists. Use this when the work has side effects outside your database, such as calling a payment provider.
3. **A version or sequence check.** Store a `version` or `updatedAt` on the row, and apply an incoming message only if its version is greater. This fixes duplicates **and** out-of-order delivery at the same time, which is why it is often the best answer for standard queues.

## 3. Lambda

### What it is

Lambda runs your code in response to an event, without you managing servers. You upload a function, AWS runs it when something happens, and you pay for the time it runs.

The mental model that matters: Lambda creates an **execution environment** (essentially a small container), runs your initialisation code once, and then reuses that environment for many invocations. Understanding what is reused and what is not explains almost every Lambda behaviour that surprises people.

### The execution lifecycle

1. **Init phase.** AWS downloads your code or container image, starts the language runtime, and runs everything at module level — imports, static blocks, code outside your handler function. This is the **cold start**. You are not billed for init on the zip package type for standard invocations, but you certainly feel the latency.
2. **Invoke phase.** Your handler runs. When it returns, the environment is **frozen**, not destroyed. Background threads stop. The next invocation to reach this environment resumes it and calls the handler again — this is a **warm start**, and the initialisation code does not run again.
3. **Shutdown phase.** After a period with no traffic, AWS destroys the environment. Extensions receive a shutdown event; your function code does not get a reliable hook.

**The practical rule that follows:** create your database clients, AWS SDK clients, HTTP connection pools, and configuration loading **outside the handler**, so they are built once per environment instead of once per request. But be careful with database connections specifically, because every concurrent environment holds its own connection — see the Aurora section below.

**The second practical rule:** never rely on state surviving between invocations, and never rely on it being cleared either. `/tmp` contents, static variables, and cached data may or may not still be there. Treat leftover state as a cache, never as a source of truth.

### Every knob explained

| Knob | Range | What it actually controls |
|---|---|---|
| **Memory** | 128 MB to 10,240 MB | This is the only performance dial. CPU is allocated **in proportion to memory**. You get roughly one full vCPU at 1,769 MB, and up to about six vCPUs at the maximum. Network bandwidth also scales with memory. So "my function is slow" is very often "my function is under-provisioned on memory even though it is not running out of memory." |
| **Timeout** | 1 second to 15 minutes | Hard ceiling. If your work can exceed 15 minutes, Lambda is the wrong compute — use Fargate, or split the work with Step Functions. |
| **Ephemeral storage** (`/tmp`) | 512 MB to 10,240 MB | Local scratch disk, reused across warm invocations. Useful for downloading a file from S3, processing it, and uploading the result. Remember to clean up, or a warm environment slowly fills. |
| **Payload size** | 6 MB synchronous request and response, 256 KB asynchronous | The synchronous limit is what caps API Gateway responses through Lambda. Bigger responses need presigned S3 URLs. |
| **Deployment package** | 50 MB zipped upload, 250 MB unzipped, 10 GB container image | Larger packages mean slower cold starts. Container images have their own layer-caching behaviour and are usually the right choice for large dependency trees. |
| **Layers** | 5 layers, counted within the 250 MB unzipped limit | Shared code and dependencies across functions. Good for shared clients and instrumentation, less good as a general dependency manager. |
| **Environment variables** | 4 KB total | Configuration. For secrets, reference Secrets Manager or SSM Parameter Store rather than putting the value here, because environment variables are visible to anyone with read access to the function configuration. |
| **Concurrency** | 1,000 per account by default, raisable to tens of thousands | The number of invocations running at the same time. This is the shared resource everything competes for. |
| **Architecture** | x86_64 or arm64 (Graviton) | Graviton is around 20 percent cheaper and often faster for the same work. Switch unless a dependency has no ARM build. |
| **VPC configuration** | Subnets and security groups | Required to reach private resources such as Aurora. Adds an elastic network interface, though Hyperplane shared interfaces have largely removed the old multi-second cold start penalty. Remember a Lambda in a VPC has no internet access unless you add a NAT gateway or VPC endpoints. |

### The concurrency model, in detail

**Concurrency** is not requests per second. It is the number of invocations in flight at one moment. The relationship is:

```
concurrency = invocations per second × average duration in seconds
```

So 100 requests per second at 200 milliseconds each needs 20 concurrent executions. The same 100 requests per second at 2 seconds each needs 200. **Making your function faster reduces concurrency use linearly**, which is why a slow database call is not just a latency problem, it is a scaling problem.

Three kinds of concurrency setting:

| Setting | What it does | Cost | When to use |
|---|---|---|---|
| **Unreserved (default)** | The function draws from the shared account pool. | Pay per use | Most functions. |
| **Reserved concurrency** | Sets a hard ceiling for this function, and simultaneously **guarantees** that much capacity is always available to it, taken out of the account pool. | Free | Two uses: capping a pipeline function so it cannot starve everything else or exhaust database connections, and guaranteeing capacity for a critical function. Setting it to 0 is also the emergency stop button for a runaway function. |
| **Provisioned concurrency** | Pre-initialises a set number of environments and keeps them warm, so there is no cold start for those. | You pay for it whether or not it is used | Latency-critical synchronous paths behind API Gateway. Combine with Application Auto Scaling to raise it before a known traffic window and lower it afterwards. |

**Burst behaviour.** From cold, an account can add a burst of concurrent executions immediately (the burst quota depends on the region, commonly in the 500 to 3,000 range), and then grows by an additional 500 concurrent executions every 10 seconds until it reaches the account limit. So Lambda scales very fast, but not instantly. A step change from 0 to 10,000 concurrent requests will throttle for the first several seconds.

**What happens when you throttle** depends on the invocation type:

- Synchronous: the caller receives `TooManyRequestsException` with HTTP 429. The caller must retry. Through API Gateway this surfaces as a 429 or 502 to the client.
- Asynchronous: Lambda retries internally for up to 6 hours, so throttles are usually invisible.
- Event source mappings: the poller backs off and retries. Nothing is lost, but the backlog grows.

**SnapStart** deserves its own mention because you write Java. SnapStart takes a snapshot of the fully initialised environment after `Init` and restores from that snapshot on cold start, rather than re-running initialisation. For a Spring Boot function this can cut cold starts from several seconds to a few hundred milliseconds. The caveats: anything that must be unique per environment (random seeds, unique identifiers) or that holds a live network connection must be re-created using the runtime hooks `beforeCheckpoint` and `afterRestore`, otherwise every restored environment shares the same "random" value and the same dead socket.

### Invocation models and error behaviour

| Model | Examples | Retry behaviour | Where failures go |
|---|---|---|---|
| **Synchronous** | API Gateway, Application Load Balancer, SDK `RequestResponse` | Lambda does not retry at all. The caller owns retries. | Nowhere. The error is returned to the caller. |
| **Asynchronous** | EventBridge, S3 notifications, SNS | Lambda queues the event internally and retries twice with backoff, for up to 6 hours of total event age. Both counts are configurable. | An **on-failure destination** (SQS, SNS, Lambda, or EventBridge) or the legacy dead letter queue. |
| **Event source mapping (poll based)** | SQS, Kinesis, DynamoDB Streams, MSK, Amazon MQ | Governed by the source. SQS retries until `maxReceiveCount`. Kinesis and DynamoDB Streams retry the batch until it succeeds or the record expires, unless you set `maximumRetryAttempts` or `bisectBatchOnFunctionError`. | SQS dead letter queue, or the `onFailure` destination for stream sources. |

**Destinations against dead letter queues.** The older dead letter queue captures only the input payload. A **destination** captures the full invocation record: the request, the response or the error, the request id, and the timestamps. Destinations are strictly better; use them for new work. They also support an on-success destination, which is a neat way to chain asynchronous steps without a full workflow engine.

### Cold starts — how to talk about them

Causes, in the order they usually matter:

1. **Heavy dependency injection frameworks.** Spring doing classpath scanning at startup is the single biggest cause of multi-second Java cold starts.
2. **Package size.** More code to download and more classes to load.
3. **Runtime.** Java and .NET start slower than Node, Python, or Go.
4. **VPC attachment.** Mostly solved by Hyperplane shared network interfaces, but still worth naming to show you know the history.

Fixes, in the order you should try them:

1. Reduce dependencies and initialise lazily anything not used on every path.
2. Use **SnapStart** for Java.
3. Use **provisioned concurrency** on latency-critical synchronous paths only, because it costs money while idle.
4. Move the workload off Lambda entirely. If a service takes sustained traffic on a user-facing path, a Fargate container has no cold start at all and often costs less.

The honest interview framing: cold starts matter on the synchronous user-facing path and barely matter on an asynchronous pipeline. Do not spend money removing cold starts from a queue consumer that nobody is waiting on.

### How Lambda scales

**What scales automatically:** the number of execution environments, up to the account concurrency limit, growing by an initial burst and then 500 more every 10 seconds.

**What you must tune by hand:**

- **Memory**, because it controls CPU and therefore duration and therefore concurrency use.
- **Reserved or maximum concurrency**, to stop one function eating the account.
- **Provisioned concurrency**, when cold starts hurt.
- **Batch size**, when the source is a queue or a stream, because processing 10 messages per invocation uses one tenth the concurrency of processing one at a time.

**What breaks first as you scale up:** almost never Lambda itself. It is the thing Lambda talks to. A thousand concurrent Lambdas mean a thousand database connections, a thousand calls per second to a third-party API with a rate limit, or a thousand writes to a DynamoDB partition. **The concurrency limit is a protection mechanism for your downstream dependencies, not a limitation of Lambda.** Say that in an interview; it shows you understand what the dial is for.

### Cost model

You pay for **gigabyte-seconds** (memory allocated multiplied by duration, billed per millisecond) plus a small per-request fee, plus provisioned concurrency if you use it.

The counter-intuitive result: **increasing memory can reduce your bill.** If doubling memory from 512 MB to 1,024 MB more than halves the duration — which it often does, because CPU doubles too — you pay less overall and get a faster function. AWS Lambda Power Tuning is a Step Functions state machine that runs your function at several memory settings and shows you the cost and speed curve. Running it and picking the optimum is a very concrete thing to say you did.

The other big lever: **do not pay for waiting.** A function idling on a slow HTTP call still bills you for full memory. Move long waits into Step Functions, which does not charge for waiting.

## 4. Step Functions

### What it is

Step Functions is a managed workflow engine. You define a state machine as JSON (Amazon States Language), and AWS runs it, keeping track of where each execution is, retrying failed steps, and recording a full history of what happened.

The reason to use it instead of writing orchestration code: **the state lives outside your code and survives failures.** If your orchestrating Lambda dies halfway through a five-step process, you have to work out what happened and clean up. If a Step Functions execution's task fails, the workflow itself is still there, knows exactly which step failed, and follows the error path you defined.

### Standard against Express — the first design decision

| | Standard | Express |
|---|---|---|
| Maximum duration | 1 year | 5 minutes |
| Execution semantics | **Exactly-once** | **At-least-once** |
| Pricing | Per state transition | Per request, plus duration multiplied by memory |
| Execution history | Full, stored and queryable through the console and API | CloudWatch Logs only |
| Throughput | Around 2,000 new executions per second, thousands of state transitions per second | Over 100,000 new executions per second |
| Invocation | Asynchronous only | Asynchronous or synchronous |
| Use it for | Long-running ETL, human approvals, sagas, anything you need to audit | High-volume short workflows, request-response API backends, per-event processing |

The pricing difference drives real design. Standard bills per state transition, so a workflow with 20 states run a million times a day gets expensive fast. Express bills like Lambda, so it is far cheaper for high volume, but you give up exactly-once and the visual execution history.

A common pattern is to combine them: a Standard workflow for the long-running overall job, which calls Express child workflows for the high-volume per-item work.

### Amazon States Language — every state type

| State | What it does |
|---|---|
| **Task** | Does actual work: invokes a Lambda, runs an ECS task, calls any AWS API, or waits for a callback token. This is the only state that does anything externally. |
| **Choice** | Branches based on the input. Supports string, numeric, boolean, timestamp, and presence comparisons, combined with `And`, `Or`, and `Not`. Always give it a `Default` branch, otherwise unmatched input fails the execution. |
| **Parallel** | Runs a fixed set of branches at the same time. Output is an array with one element per branch. Use when you have a known, small number of independent things to do. |
| **Map** | Runs the same steps once per item in an array. Use when the number of things is dynamic. |
| **Pass** | Passes input through, optionally reshaping or injecting fixed data. Great for restructuring between steps and for stubbing a step during development. |
| **Wait** | Pauses for a fixed number of seconds, or until an absolute timestamp. **You are not billed for the wait time**, which makes this dramatically cheaper than a Lambda sleeping. |
| **Succeed** | Ends the execution successfully. |
| **Fail** | Ends the execution with an error name and cause you choose. |

**Inline Map against Distributed Map** — this distinction comes up constantly.

- **Inline Map** takes its items from the state input (so they must fit inside the 256 KB payload limit) and runs up to **40 concurrent iterations**. Fine for tens or hundreds of items.
- **Distributed Map** reads its items directly from **S3** — a JSON array, a CSV file, an S3 inventory list, or a list of objects under a prefix — and runs up to **10,000 parallel child executions**. It supports item batching, a tolerated failure percentage or count, and writing the combined results back to S3.

Distributed Map is the tool purpose-built for "process one million records." It is worth naming even if you actually solved the problem with SQS and Lambda, because it shows you know the alternative and can compare them: Distributed Map gives you built-in progress tracking, failure tolerance, and result aggregation; SQS plus Lambda gives you finer-grained retry per message, cheaper unit economics at very high volume, and no state-transition billing.

### Data flow inside a state — the part people always get wrong

Each state processes data in a fixed sequence of filters:

1. **`InputPath`** — selects a portion of the state input to work with. Default is the whole thing.
2. **`Parameters`** — builds the actual payload sent to the task, letting you mix constants with values pulled from the input using `.$` and JSONPath.
3. The task runs and produces a result.
4. **`ResultSelector`** — picks apart the raw task result before it goes anywhere.
5. **`ResultPath`** — decides where the result is placed relative to the state's original input. This is the important one: `ResultPath: "$.taskOutput"` **keeps the original input and adds the result under a new key**, while omitting it replaces the input entirely with the result. Losing your input because you forgot `ResultPath` is the most common Step Functions bug.
6. **`OutputPath`** — selects the portion of the combined result to pass to the next state.

### Error handling

```json
"Retry": [{
  "ErrorEquals": ["States.TaskFailed", "Lambda.ServiceException"],
  "IntervalSeconds": 2,
  "MaxAttempts": 4,
  "BackoffRate": 2.0,
  "MaxDelaySeconds": 60,
  "JitterStrategy": "FULL"
}],
"Catch": [{
  "ErrorEquals": ["States.ALL"],
  "Next": "CompensateInventory",
  "ResultPath": "$.error"
}]
```

| Field | What it controls |
|---|---|
| `ErrorEquals` | Which errors this rule applies to. Retry blocks are evaluated in order, so put specific errors before `States.ALL`. |
| `IntervalSeconds` | Wait before the first retry. |
| `MaxAttempts` | How many retries. Zero means "match this error but do not retry", useful for excluding an error from a broader rule below it. |
| `BackoffRate` | Multiplier applied to the interval each attempt. 2.0 gives 2, 4, 8, 16 seconds. |
| `MaxDelaySeconds` | Caps the backoff so it does not grow without bound. |
| `JitterStrategy` | `FULL` randomises the wait. **Use it.** Without jitter, a thousand executions that all failed at the same moment all retry at the same moment, and hammer the recovering dependency back down. |
| `Catch` | Where to go when retries are exhausted. `ResultPath: "$.error"` preserves the original input and adds the error details, so your handler knows both what failed and what it was working on. |

Built-in error names: `States.ALL`, `States.TaskFailed`, `States.Timeout`, `States.Permissions`, `States.DataLimitExceeded`, `States.HeartbeatTimeout`, `States.Runtime`, plus any custom error your own code throws.

### Service integrations — three kinds

| Kind | How it behaves | Example |
|---|---|---|
| **Request and response** (default) | Calls the service and immediately moves on, without waiting for the work to finish. | Publishing to SNS. |
| **Run a job** (`.sync`) | Calls the service and **waits for the job to complete**, then continues. Step Functions polls for you. | `ecs:runTask.sync`, Glue jobs, EMR steps, AWS Batch, and nested Step Functions executions. This is how you run a container that takes 40 minutes as one step in a workflow. |
| **Wait for callback** (`.waitForTaskToken`) | Passes a task token to the target and pauses, possibly for up to a year, until something calls `SendTaskSuccess` or `SendTaskFailure` with that token. | Human approval steps, third-party systems that call you back, and anything requiring an out-of-band signal. |

There are also **AWS SDK integrations**, which let a Task state call roughly 200 AWS services directly. This removes an enormous amount of Lambda glue code: you no longer write a function whose entire body is one `PutItem` call.

### Saga pattern in Step Functions

A saga is how you get something like a transaction across services that have no shared transaction. Instead of rolling back, you run a **compensating action** for each step that already succeeded.

In Step Functions this maps directly: each forward step is a Task, each has a `Catch` pointing at its compensating task, and the compensating tasks chain backwards to undo the earlier steps. The state machine itself becomes the saga log — durable, inspectable, and visual.

If you implemented a saga in application code instead, be ready to explain the trade-off honestly: "We owned the orchestrator in our own service because the compensation logic needed domain knowledge and we wanted the pipeline in one deployable unit. Step Functions would have given us durability and visual debugging for free, at the cost of per-state-transition pricing and the 256 KB payload limit between states."

### Limits

| Limit | Value | What to do about it |
|---|---|---|
| Payload between states | 256 KB | Pass S3 references, not data. Same claim-check idea as everywhere else. |
| Execution history events | 25,000 for a Standard execution | Long loops blow through this. Use Distributed Map, or start child executions so each has its own history budget. |
| Execution duration | 1 year Standard, 5 minutes Express | — |
| Express history | Not stored | Debug through CloudWatch Logs, and turn logging on before you need it. |
| State machine definition size | 1 MB | Very large generated workflows can hit this. |

### How Step Functions scales

**Standard** handles roughly 2,000 new executions per second and a few thousand state transitions per second per account, as soft raisable limits. Because you pay per transition, cost usually becomes the constraint before the limit does.

**Express** handles more than 100,000 new executions per second and is the right answer whenever volume is high.

**Distributed Map** is the scaling feature. It goes to 10,000 concurrent child executions and reads its work list from S3, so the size of the input is bounded by S3 rather than by a payload limit. When you use it, remember the child executions all hit the same downstream dependency — set `MaxConcurrency` on the map to something your database or third-party API can actually survive, not to the maximum.

## 5. Kinesis Data Streams

### What it is

Kinesis Data Streams is an ordered, replayable log. Producers write records into the stream; the stream keeps them for a retention period; consumers read from a position in the log and move forward at their own pace.

The difference from SQS in one sentence: **a queue deletes a message once someone processes it; a log keeps every record for its retention period and lets many independent consumers read the same records.**

### Every concept explained

**Shards.** A shard is the unit of capacity and the unit of ordering. One shard gives you:

- 1 MB per second or 1,000 records per second of write throughput
- 2 MB per second of read throughput, **shared across all standard consumers**
- Or 2 MB per second **per consumer** if you use Enhanced Fan-Out

Total stream capacity is simply shard count multiplied by these numbers. This is the key structural difference from SQS: **Kinesis capacity is something you provision and plan, SQS capacity is not.**

**Partition key.** Every record you write carries a partition key. Kinesis takes the MD5 hash of that key and uses it to pick a shard. Two consequences follow:

- All records with the same partition key go to the same shard, and therefore are read **in order**. Ordering in Kinesis is per partition key, never across the whole stream.
- If one key is much more popular than the others, its shard receives far more traffic than the rest. This is a **hot shard**.

**Sequence number.** Kinesis assigns each record an increasing sequence number within its shard. Consumers checkpoint by sequence number, and you can start reading from a specific sequence number or a specific timestamp — this is what makes replay possible.

**Retention.** 24 hours by default, extendable up to 365 days. Within the retention window you can rewind a consumer and reprocess everything. SQS cannot do this at all, and it is usually the deciding factor when choosing between them.

**Capacity modes:**

| Mode | How it works | When to use |
|---|---|---|
| **Provisioned** | You choose the shard count and change it yourself by splitting and merging shards. Cheapest per unit at steady, predictable load. | Known, stable traffic. Also the only mode where you fully control ordering-affecting resharding. |
| **On-demand** | Kinesis scales shards automatically based on observed traffic, up to double the peak of the last 30 days. Higher price per unit. | Unpredictable or spiky load, and new workloads where you do not yet know the shape of the traffic. |

**Consumers:**

| Consumer type | How it reads | Latency | Throughput |
|---|---|---|---|
| **Standard (shared throughput)** | Polls with `GetRecords`. All consumers of a shard share the same 2 MB per second. | ~200 ms and up, worse with more consumers | 2 MB/s per shard, shared |
| **Enhanced Fan-Out** | Kinesis pushes to the consumer over HTTP/2. Each registered consumer gets its own throughput. | ~70 ms | 2 MB/s per shard, per consumer |

Enhanced Fan-Out costs extra per consumer-shard-hour, but it is the answer when you have more than two or three consumers on the same stream and they are starving each other.

**Checkpointing.** The Kinesis Client Library keeps leases and checkpoints in a DynamoDB table it manages for you — one row per shard, recording which worker owns it and how far it has read. This is how consumers rebalance when you add or remove workers. Lambda event source mappings handle the equivalent internally, checkpointing per batch.

### The metric that matters: `IteratorAge`

`IteratorAge` is how far behind the head of the stream your consumer is, measured in time. It is the single most important Kinesis metric and you should alarm on it.

A rising iterator age means one of two things:

1. Your consumers are too slow or too few for the incoming volume.
2. A **poison record** is failing repeatedly at the head of a shard.

That second case is the crucial difference from SQS. In SQS, a bad message goes to the dead letter queue and everything else keeps flowing. In Kinesis, **a record that keeps failing blocks its entire shard**, because ordering must be preserved and the consumer cannot move past it. Every good record behind it waits.

The fixes, all configured on the Lambda event source mapping:

- `bisectBatchOnFunctionError` — on failure, split the batch in half and retry each half, repeatedly, to isolate the single bad record instead of failing the whole batch.
- `maximumRetryAttempts` — give up after N attempts rather than retrying until the record expires.
- `maximumRecordAgeInSeconds` — skip records older than this.
- `onFailure` destination — send the failed record's metadata to an SQS queue or SNS topic so you can investigate it, while the shard moves on.

Configure all four. A Kinesis consumer without them will eventually stall on a bad record and you will find out from a customer.

### How Kinesis scales

This is the service where scaling is the most manual, so it is a favourite interview topic.

**Scaling up in provisioned mode** means **resharding**: you split a shard into two, which doubles capacity for that key range. Splitting closes the parent shard and opens two children. Consumers must finish the parent before reading the children, so ordering is preserved across the split, but there is a brief period where the shard layout is changing. Merging two adjacent shards is the reverse. Resharding is an API operation and takes time; you cannot do it instantly in response to a spike.

**Scaling in on-demand mode** is automatic, but not instant. Kinesis roughly doubles capacity in response to sustained increases and can take several minutes to react. A truly instantaneous spike will still throttle producers with `ProvisionedThroughputExceededException` — so producers need retry with backoff regardless of mode.

**Hot shards, the classic problem.** If your partition key is `storeId` and one store generates 60 percent of your traffic, that store's shard is at capacity while the others sit nearly idle. Adding shards does not help, because the hash sends that key to one place regardless.

Two ways to fix it:

1. **Composite key.** Use `storeId#bucket`, where bucket is a small random or round-robin number. This spreads one store across several shards. The cost is that you have given up strict ordering within that store, so only do this when the store's records do not need to be ordered relative to each other — or when you can restore order downstream with a version number.
2. **Move the ordering requirement.** Often you do not actually need ordering across all of a store's events, only across events for a single product or a single order. Using the narrower key gives natural spread and keeps the ordering you actually need.

**Scaling consumers.** Concurrency is bounded by shard count: one Lambda invocation per shard at a time by default. The `ParallelizationFactor` setting raises this to up to 10 concurrent invocations per shard, while still preserving order **per partition key**. This is the cheapest way to speed up a lagging consumer without resharding, and it is a good detail to volunteer.

**When to prefer Kinesis over SQS:** you need replay, you need several independent consumers reading the same records, or you need strict per-key ordering at high volume.

**When SQS wins:** independent work items with no ordering requirement, elastic per-message parallelism, simple retry and dead letter queue semantics, and no capacity planning at all. For most business workloads SQS is the right default, and Kinesis is the specialised choice.

## 6. API Gateway

### What it is

API Gateway is a managed front door for your APIs. It terminates HTTPS, authenticates and authorises the caller, throttles them, optionally validates and transforms the request, and forwards it to a backend — a Lambda, an HTTP endpoint, a load balancer inside your VPC, or an AWS service API directly.

### The three flavours

| | REST API | HTTP API | WebSocket API |
|---|---|---|---|
| Price | Highest | Roughly 70 percent cheaper | Per message and per connection minute |
| Latency | Higher | Lower | — |
| Request validation | Yes, against JSON Schema models | No | No |
| Transformation | Yes, VTL mapping templates | Limited parameter mapping only | Limited |
| Caching | Yes, per stage, 0.5 GB to 237 GB | No | No |
| API keys and usage plans | Yes | No | No |
| Authorizers | IAM, Cognito, Lambda (token or request) | IAM, JWT, Lambda | IAM, Lambda |
| Web Application Firewall | Yes | Yes (regional) | No |
| Private endpoints | Yes | No | No |
| Canary deployments | Yes | No, use stages and weighted routing | No |

**How to choose:** start with HTTP API. Move to REST API only when you specifically need request validation, response caching, usage plans with API keys, private endpoints, or VTL transformation. The price difference is real at volume, and most of the REST API features are things you either do not need or can do just as well in your own code.

**WebSocket API** works differently: you define routes for `$connect`, `$disconnect`, and your own custom routes, and AWS gives each connection an identifier. To push a message to a client you call the `@connections` management API with that connection identifier. You must store the connection identifiers yourself, usually in DynamoDB, and clean up stale ones when the management API returns 410 Gone.

### Authentication and authorisation options

| Option | How it works | Best for |
|---|---|---|
| **IAM (SigV4)** | The caller signs the request with AWS credentials. API Gateway verifies the signature and evaluates IAM policies. | Service-to-service calls inside AWS, and internal tooling. |
| **Cognito user pools** | API Gateway validates a Cognito-issued token directly. | Applications already using Cognito for user sign-in. |
| **Lambda authorizer** | Your own function receives the token or the whole request, and returns an IAM policy document plus a context object that is passed on to the backend. **The result is cacheable by a TTL** (up to one hour), so you do not pay to validate the same token on every request. | Custom authentication logic, third-party identity providers, per-tenant rules. The most flexible option. |
| **JWT authorizer** | Built into HTTP API. You give it the issuer and audience, and it validates the token natively with no code. | Standard OIDC or OAuth 2.0 providers such as Auth0 or Okta. Prefer this over a Lambda authorizer when it fits, because it is faster and free. |
| **mTLS** | Client presents a certificate that API Gateway validates against a truststore you keep in S3. Configured on a custom domain. | Partner integrations and business-to-business APIs with strong identity requirements. |

There are two Lambda authorizer types worth distinguishing: **TOKEN** type receives just the token from a single header and is easy to cache; **REQUEST** type receives headers, query parameters, path parameters, and context, which is more powerful but has a more complex cache key.

### Throttling and quotas

There are several layers, and they are applied from the outside in:

1. **AWS account level.** Around 10,000 requests per second per region by default, with a burst bucket of around 5,000. Raisable.
2. **Stage level.** You set a rate and burst for the whole stage.
3. **Method level.** You set a rate and burst per individual route, so one expensive endpoint cannot consume the whole API's budget.
4. **Usage plans with API keys** (REST API only). Per-client rate, burst, and **quota** — for example 10,000 requests per day per key. This is how you build tiered plans for external customers.

The throttling model is a **token bucket**: the rate is how fast tokens refill, the burst is how many can accumulate. So a rate of 100 per second with a burst of 200 allows a sudden spike of 200 requests, then settles at 100 per second.

Excess requests get HTTP 429 with a `Retry-After` indication. Surface that clearly to clients rather than turning it into a generic 500, because a well-behaved client will back off correctly if you tell it the truth.

### Integration types

| Integration | What it does | Notable use |
|---|---|---|
| **Lambda proxy** | The whole HTTP request is passed to Lambda as a JSON event; your function returns status code, headers, and body. | The default. Simple, no VTL to maintain, and all the logic stays in code you can test. |
| **Lambda non-proxy** | You map the request into a Lambda payload and map the response back, using VTL templates. | Only when you need API Gateway to own the contract shape independently of the function. Adds a template language nobody enjoys debugging. |
| **HTTP and HTTP proxy** | Forwards to any HTTP endpoint. | Putting API Gateway's auth, throttling, and metrics in front of an existing service. |
| **AWS service integration** | Calls an AWS API directly with no compute in between. | **Straight to SQS** is the standout use: an endpoint that accepts a burst of requests and drops them into a queue, with no Lambda to throttle and no cold start. Excellent for high-volume ingestion. Also useful straight to DynamoDB, Kinesis, and Step Functions. |
| **VPC Link** | Private connection to an internal Application or Network Load Balancer. | Exposing an ECS or EKS service that has no public address. |
| **Mock** | Returns a canned response with no backend at all. | CORS preflight responses and API stubs during development. |

### Other properties you should know

- **Integration timeout is 29 seconds** on REST APIs and by default on HTTP APIs (raisable on REST APIs by request). This is a hard architectural constraint. Any job that can take longer must return **202 Accepted** with a status URL, and the client polls or gets notified. Do not try to make a long job fit in 29 seconds.
- **Endpoint types**: edge-optimised (routed through CloudFront points of presence, good for globally distributed clients), regional (better when clients are in the same region, or when you want your own CloudFront distribution in front), and private (reachable only from inside your VPC through an interface endpoint).
- **Stages and stage variables**: a stage is a deployed snapshot, for example `dev`, `staging`, `prod`. Stage variables let one definition point at different backend Lambda aliases or HTTP endpoints per stage.
- **Canary release**: send a percentage of traffic on a stage to a new deployment, watch the metrics, then promote or roll back. Built into REST API stages.
- **Request validation** against JSON Schema models rejects malformed requests before they reach your compute. This is your **data contract enforced at the edge**, it costs nothing to run, and it removes a class of defensive code from every backend function.
- **Caching** (REST API only): a per-stage cache with a configurable size and TTL, keyed on request parameters you choose. It can remove most of the load from a read-heavy endpoint. Remember to allow authorised cache invalidation, and never cache a response that varies by user unless the user identity is part of the cache key.

### How API Gateway scales

**What scales automatically:** API Gateway itself. It is a managed regional service and handles very high request rates without any provisioning. Your account limit is the ceiling, and it is raisable.

**What breaks first:** the backend. API Gateway will happily accept 10,000 requests per second and try to invoke your Lambda 10,000 times, which throttles at the account concurrency limit. The gateway is not the bottleneck; the thing behind it is.

**The scaling levers, in the order you should reach for them:**

1. **Caching** (REST API). The cheapest possible scaling: a cached response never touches your backend at all.
2. **Throttling at the method level.** Protect the backend by rejecting excess load at the edge with a fast 429, rather than letting it queue up and time out. Failing fast is better than failing slowly.
3. **Usage plans**, so one badly behaved client cannot consume the capacity of all the others.
4. **Direct service integration to SQS** for write-heavy ingestion endpoints. This decouples the accept rate from the process rate completely: the API accepts everything at gateway speed, and the consumer drains at its own pace. This is the single best pattern for "we get a burst of ten thousand submissions in one minute."
5. **Provisioned concurrency** on the Lambda behind latency-sensitive routes, so a traffic ramp does not produce a wall of cold starts.

## 7. ECS Fargate

### What it is

ECS is AWS's container orchestrator. Fargate is the mode where AWS runs the containers for you, so there are no EC2 instances to patch, scale, or bin-pack.

### The object model

| Object | What it is |
|---|---|
| **Task definition** | The blueprint. Specifies the container image or images, CPU and memory, environment variables, secrets, port mappings, log configuration, and the two IAM roles. Immutable and versioned — every change creates a new revision. |
| **Task** | A running instance of a task definition. One or more containers that share a network namespace, scheduled together, on the same host. |
| **Service** | Keeps a desired number of tasks running, registers them with a load balancer, replaces unhealthy ones, and performs rolling deployments. Use a service for anything long-running; run a standalone task for batch jobs. |
| **Cluster** | A logical grouping of services and tasks. With Fargate it is little more than a namespace and a boundary for capacity providers. |

**The two IAM roles, which people constantly confuse:**

- **Task execution role** — used by the ECS agent, *before and around* your container. It pulls the image from ECR, fetches secrets from Secrets Manager or SSM to inject as environment variables, and writes logs to CloudWatch.
- **Task role** — used by **your application code** at runtime to call AWS APIs. This is where you grant `s3:GetObject` or `sqs:SendMessage`.

Getting these backwards is a very common source of "why can my container not read from S3."

### Fargate specifics

- **No hosts.** No AMIs to patch, no instance types to choose, no capacity to bin-pack. Billed per second based on the vCPU and memory you request, with a one-minute minimum.
- **`awsvpc` networking.** Every task gets its own elastic network interface, its own private IP address, and its own security group. This means you can write security group rules between individual services, which is much finer-grained than instance-level rules.
- **Fixed CPU and memory combinations.** You cannot request arbitrary values. CPU goes 0.25, 0.5, 1, 2, 4, 8, and 16 vCPU, and each CPU size allows a specific range of memory. Choose the combination, not independent numbers.
- **Ephemeral storage** of 20 GB by default, configurable up to 200 GB. For persistent storage, mount EFS.
- **Platform version** controls the underlying Fargate features available. Pin it if you depend on something specific; otherwise `LATEST` is fine.

### Scaling ECS Fargate

Fargate has **two independent layers of scaling**, and a good answer mentions both.

**Layer one: the number of tasks (horizontal scaling).** This is Application Auto Scaling adjusting the service's desired count.

| Policy type | How it works | When to use |
|---|---|---|
| **Target tracking** | You pick a metric and a target value, and AWS adds or removes tasks to keep the metric near that value. Available metrics: average CPU utilisation, average memory utilisation, and **ALB request count per target**. | The default choice, and correct for almost everything. Request count per target is usually the best signal, because it responds before CPU does and it maps directly to the work arriving. |
| **Step scaling** | You define CloudWatch alarm thresholds and how many tasks to add or remove at each threshold. | When you need different responses at different severities, for example add 2 tasks at 60 percent and 10 tasks at 85 percent. |
| **Scheduled scaling** | Change minimum and maximum capacity at fixed times. | Known traffic patterns: business hours, nightly batch windows, a scheduled marketing event. Combine with target tracking so the schedule sets the floor and the metric handles the rest. |

Important properties on a scaling policy:

- **Scale-out cooldown** — how long to wait after scaling out before considering another scale-out. Keep this short, because being slow to add capacity hurts users.
- **Scale-in cooldown** — how long to wait before removing tasks. Keep this long, because removing capacity too eagerly causes flapping, and the cost saving is small compared with the risk.
- **Minimum and maximum capacity** — the maximum is your protection against a runaway bill and against overwhelming your database. Always set it deliberately.

**Layer two: the size of each task (vertical scaling).** Changing CPU and memory in the task definition. Bigger tasks are more efficient per unit of work for JVM applications, because you amortise the heap and the warm-up over more requests. Smaller tasks give finer-grained scaling and faster start-up. For Spring Boot, a small number of larger tasks usually beats a large number of tiny ones.

**The timing point that matters most:** a Fargate task takes roughly **30 to 60 seconds to start** — pulling the image, attaching the network interface, starting the runtime, and passing health checks. For a JVM application with a slow start-up it can be longer. Compare that with Lambda, which adds capacity in milliseconds to seconds.

The practical consequence: **you must scale Fargate earlier than you would scale Lambda.** Set your target utilisation lower (55 to 65 percent rather than 80 percent) so there is headroom while new tasks boot. Keep a warm minimum count so you are never starting from one task. Optimise your image size, because the pull is a real part of that start-up time.

**Health checks, which are part of scaling correctness:**

- **Container health check** (in the task definition) — a command run inside the container.
- **Load balancer health check** — the target group calls a path on your task. A task that fails this is deregistered and replaced.
- **Health check grace period** on the service — how long after a task starts before load balancer health checks count against it. If this is too short for a slow-starting JVM application, ECS kills the task while it is still warming up, starts another, and you get an infinite restart loop. This is one of the most common ECS misconfigurations.

### Deployments

- **Rolling update** (default), controlled by two percentages: `minimumHealthyPercent` (how far below desired count you are willing to drop during a deploy) and `maximumPercent` (how far above). Setting 100 and 200 means new tasks fully start before old ones are removed, with no capacity dip and double cost briefly.
- **Deployment circuit breaker** — automatically detects a failing deployment and rolls back to the previous task definition. Turn it on. It costs nothing and it prevents the most common bad night.
- **Blue/green with CodeDeploy** — brings up a full replacement set behind a test listener, lets you validate it, then shifts production traffic all at once, linearly, or in a canary. Automatic rollback on CloudWatch alarms. More infrastructure and more time, but the safest option for a critical service.

### Cost and other features

- **Fargate Spot** — up to around 70 percent cheaper, with a two-minute interruption warning. Perfect for queue consumers and batch work that can be restarted; never for a stateful service that cannot tolerate a sudden stop. Use a capacity provider strategy to mix, for example a base of on-demand tasks for reliability plus Spot for everything above it.
- **Compute Savings Plans** apply to Fargate, so committed steady-state capacity gets a substantial discount.
- **Service Connect and Cloud Map** — service discovery, so tasks find each other by name rather than by IP address, with built-in connection metrics.
- **Scale-in protection** — mark a task as protected while it is in the middle of a long job so auto-scaling does not kill it half way. Essential for queue consumers processing long-running messages.

### Lambda against Fargate against EKS — the decision framework interviewers want

| | Lambda | Fargate | EKS |
|---|---|---|---|
| Scaling speed | Milliseconds to seconds | 30 to 60 seconds | 30 to 60 seconds, faster with over-provisioned nodes |
| Maximum runtime | 15 minutes | Unlimited | Unlimited |
| Idle cost | Zero | You pay for running tasks | You pay for nodes and the control plane |
| Cost at high sustained load | Expensive | Cheaper | Cheapest at large scale, but add the platform team |
| Cold start | Yes | No, once the task is warm | No |
| Operational burden | Lowest | Low | Highest |
| Best for | Spiky, event-driven, short work | Steady load, long jobs, big containers, gRPC and WebSocket | Kubernetes primitives, portability, service mesh, or a team already running it |

The crossover point is roughly this: Lambda is cheaper below a certain steady request rate, and Fargate is cheaper above it, because Lambda charges per request while a container's cost is flat once it is running. Spiky traffic favours Lambda; flat traffic favours containers. Being able to say that out loud, with the reasoning, is worth more than remembering an exact number.

## 8. S3

### What it is

S3 is object storage. You put objects into buckets under a key, and get them back by key. It is not a file system: there are no real directories, only keys that contain slashes and a listing API that can group by prefix.

In an event-driven architecture S3 plays two specific roles: it is the **claim-check store** for payloads too large for a message, and it is the **durable archive** that makes reprocessing and auditing possible.

### The properties that matter

**Consistency.** Since December 2020 S3 gives **strong read-after-write consistency** for all operations, including PUTs of new objects, overwrites, deletes, and LIST. The old "eventual consistency" caveats and the workarounds people built for them are gone. Say this confidently; a surprising number of candidates still repeat the old behaviour.

**Storage classes and lifecycle.**

| Class | Retrieval | Minimum duration | Use for |
|---|---|---|---|
| Standard | Immediate | None | Active data. |
| Intelligent-Tiering | Immediate | None | Unknown or changing access patterns. It moves objects between tiers automatically for a small monitoring fee per object. The safe default when you genuinely do not know. |
| Standard-Infrequent Access | Immediate | 30 days | Data you rarely read but need instantly when you do. Cheaper storage, but you pay a retrieval fee per gigabyte. |
| Glacier Instant Retrieval | Immediate | 90 days | Archives you occasionally need right away. |
| Glacier Flexible Retrieval | Minutes to hours | 90 days | Backups and compliance archives. |
| Glacier Deep Archive | Around 12 hours | 180 days | Long-term legal retention. Cheapest storage in AWS. |

A **lifecycle rule** moves objects between classes and eventually expires them, based on age and filtered by prefix or tag. This is exactly how you justify "S3 archival for auditability at low cost": raw files land in Standard, move to Standard-Infrequent Access after 30 days, to Glacier after 90, and expire after seven years. Configure it once and it runs forever.

Watch the minimum duration charges. Moving an object to Glacier and deleting it a week later still bills you for 90 days, so aggressive lifecycle rules on short-lived data can increase your bill.

**Versioning and Object Lock.** Versioning keeps every version of an object, so an overwrite or delete is recoverable — a delete just adds a delete marker. **Object Lock** goes further and gives you write-once-read-many behaviour: in governance mode, only users with a specific permission can remove the retention; in compliance mode, **nobody** can, not even the account root, until the retention period expires. Add a legal hold for indefinite retention. This is a real compliance answer, not a hand-wave, and it is worth knowing the difference between the two modes.

**Event notifications.** S3 can notify SQS, SNS, Lambda, or EventBridge when objects are created, deleted, restored, or replicated, filtered by prefix and suffix. This is the classic ingestion trigger: a file lands, a pipeline starts. Prefer routing to EventBridge when you want several independent consumers or richer filtering; use direct-to-SQS when you want a simple buffered pipeline with one consumer.

**Performance and prefixes.** S3 supports around **3,500 write operations and 5,500 read operations per second per prefix**, and there is no limit on the number of prefixes. So throughput is essentially unlimited if you spread keys across prefixes, and badly limited if you put everything under one. A key like `raw/2026-08-06/<sequential-id>.xml` concentrates all of a day's traffic on one prefix; adding a hash or a source component spreads it.

**Multipart upload.** Required above 5 GB, and worth using above around 100 MB anyway, because parts upload in parallel and a failed part is retried on its own instead of restarting the whole upload. Always set a lifecycle rule to abort incomplete multipart uploads after a few days, otherwise you pay storage for abandoned parts you cannot even see in a normal listing. This is a genuinely common hidden cost.

**Presigned URLs.** A time-limited URL that lets a client upload or download directly, using your permissions, without going through your API. This keeps large files off your compute entirely — no Lambda payload limit, no API Gateway timeout, no bandwidth cost through your service. For any "users upload documents" feature this should be your default design.

**Security controls, layered:**

- **Encryption at rest**: SSE-S3 (AWS-managed keys, free, on by default) against SSE-KMS (your key, per-key permissions, CloudTrail audit trail, but KMS API calls cost money and have throttling limits — use S3 Bucket Keys to cut those calls by a large factor) against SSE-C (you supply the key on every request).
- **Bucket policies** (resource-based, control access to the bucket), **IAM policies** (identity-based), and **ACLs** (legacy, and best disabled entirely by setting bucket ownership to enforced).
- **Block Public Access** — turn it on at both account and bucket level unless you have a specific, reviewed reason not to.
- **VPC gateway endpoint** — S3 traffic from inside your VPC goes over the AWS network instead of out through a NAT gateway. This is both a security improvement and often a large cost saving, because NAT gateway data processing charges add up quickly on a data-heavy pipeline.

**Querying data in place.** S3 Select reads a subset of a single object. Athena, backed by Glue, runs SQL across many objects and uses your prefix structure as partitions. This is how you answer "can you go back and inspect the raw XML we received six months ago?" without building anything new.

### Key layout matters more than people expect

```
raw/dt=2026-08-06/source=partnerA/<id>.xml
```

This single scheme gives you four things at once: lifecycle rules that can target a date range, Athena partitioning on both date and source (so a query for one partner on one day scans almost nothing), prefix parallelism for high-volume writes, and human-readable navigation when you are debugging at 2 in the morning. Design it before you write the first object, because renaming keys later means copying everything.

### How S3 scales

S3 scales essentially without limit on storage and object count. Request throughput scales with prefix count as described above, and S3 also adapts internally to sustained traffic patterns over time.

The things that actually bite:

- **A single hot prefix.** Fix with a better key design.
- **Request cost.** At very high volume, per-request charges can exceed storage charges. Fewer, larger objects are cheaper than many tiny ones. If you are writing millions of small objects, consider batching them.
- **KMS throttling.** If every object read decrypts through KMS, you can hit KMS request limits before you hit any S3 limit. S3 Bucket Keys fix this.
- **Listing large prefixes.** `ListObjectsV2` paginates at 1,000 keys. Listing a prefix with ten million objects is slow and expensive. Use S3 Inventory (a daily report delivered as a file) instead of listing, and use Distributed Map in Step Functions to process the inventory.

## 9. CloudWatch

See also `07-observability.md` for the wider observability discussion. This section covers the AWS-specific mechanics.

### Metrics

A metric is identified by a **namespace** (for example `AWS/Lambda` or your own `Elevation/Ingestion`), a **name**, and a set of **dimensions** (key-value pairs such as `FunctionName=processor`). Every unique combination of dimensions is a **separate metric** for billing purposes.

That last point is the one that costs people money. Custom metrics are billed **per metric per month**. If you add a `customerId` dimension and you have 50,000 customers, you have just created 50,000 metrics. Cardinality is the cost driver, and it is very easy to create by accident.

- **Resolution**: standard metrics are one-minute granularity. High-resolution custom metrics go down to one second, cost more, and are rarely worth it outside genuinely fast-moving systems.
- **Statistics**: sum, average, minimum, maximum, sample count, and percentiles. **Always look at p99, not average.** An average latency of 100 milliseconds can hide a p99 of 8 seconds, and the p99 is what your users complain about.
- **Metric maths** lets you build derived metrics — error rate as errors divided by invocations, for example — and alarm on those rather than on raw counts, which is much more stable as traffic varies.

**Embedded Metric Format** is the way to instrument cheaply. You write a specially structured JSON line to your logs, and CloudWatch automatically extracts metrics from it. You get the metric for dashboards and alarms, and you keep the full high-cardinality log line for investigation, without paying per-metric prices for every dimension combination. From Lambda this is the recommended approach and it needs no extra API call in the hot path.

### Logs

- **Log groups** hold log streams. **Set a retention period on every log group.** The default is "never expire", which is silently one of the most common AWS cost bugs. Most application logs are worthless after 30 days; keep audit logs longer and deliberately.
- **Logs Insights** is the query language. Learn `filter`, `stats ... by`, `sort`, and `parse` — those four cover the vast majority of incident investigation.
- **Subscription filters** stream matching log events in near real time to Kinesis, Firehose, Lambda, or OpenSearch. This is how you get logs into Datadog, Splunk, or your own store, and how you build alerting on log content rather than on metrics.
- **Log ingestion is billed per gigabyte ingested**, and it is often a bigger line item than storage. Debug logging left on in production at high volume is a genuinely expensive mistake.

### Alarms

| Feature | What it does |
|---|---|
| **Static threshold** | Alarm when a metric crosses a fixed value. |
| **Anomaly detection** | CloudWatch models the normal band for the metric and alarms when it leaves that band. Good for metrics with a daily or weekly shape where a fixed threshold would be wrong at some times of day. |
| **M out of N datapoints** | Only alarm when, say, 3 of the last 5 periods breach. Kills most flapping. |
| **`treatMissingData`** | What to do when there is no data: `notBreaching`, `breaching`, `ignore`, or `missing`. This matters more than it looks. A queue that has stopped receiving messages produces no datapoints, and if you treat that as "not breaching" you will never find out that your producer died. |
| **Composite alarms** | Combine alarms with boolean logic. The classic use is noise suppression: alert only if the error rate is high **and** a deployment is not currently in progress. Also useful for a single "service is unhealthy" alarm built from several signals. |

### Tracing

**X-Ray** traces a request across services: API Gateway to Lambda to SQS to another Lambda to Aurora. Key concepts:

- **Segments and subsegments** — one segment per service, subsegments for individual calls such as a database query.
- **Sampling rules** — you do not trace every request. The default is one request per second plus 5 percent of the rest. Tune this per route; trace more of the important ones.
- **Annotations against metadata** — annotations are indexed and searchable, so put your identifiers there (`orderId`, `tenantId`). Metadata is stored but not indexed, so put bulky context there. Getting this wrong means you have the trace but cannot find it.

**ServiceLens** joins traces, metrics, and logs into one service map view.

### The metrics you should name for your pipelines

Being able to reel these off is a strong signal in an interview:

| Service | Metrics that matter | Why |
|---|---|---|
| SQS | `ApproximateAgeOfOldestMessage`, `ApproximateNumberOfMessagesVisible` on the dead letter queue | Age is the real backlog indicator. Dead letter queue depth above zero always means a human should look. |
| Lambda | `Errors`, `Throttles`, `Duration` p99, `ConcurrentExecutions`, `IteratorAge` for stream sources | Throttles mean you are hitting a concurrency ceiling. p99 duration drives both cost and concurrency use. |
| EventBridge | `FailedInvocations`, `ThrottledRules`, `DeadLetterInvocations` | These are the only way to find out that events are being lost. |
| Kinesis | `IteratorAge`, `WriteProvisionedThroughputExceeded`, `ReadProvisionedThroughputExceeded` | Iterator age is the health of the whole stream. Throughput exceptions mean it is time to reshard. |
| Step Functions | `ExecutionsFailed`, `ExecutionsTimedOut`, `ExecutionThrottled` | — |
| API Gateway | `4XXError`, `5XXError`, `Latency`, `IntegrationLatency`, `Count` | The gap between `Latency` and `IntegrationLatency` is the gateway's own overhead, which separates "my backend is slow" from "the gateway is slow". |
| ECS | `CPUUtilization`, `MemoryUtilization`, `RunningTaskCount`, plus ALB `TargetResponseTime` and `UnHealthyHostCount` | — |
| Aurora | `DatabaseConnections`, `CPUUtilization`, `AuroraReplicaLag`, `Deadlocks`, `BufferCacheHitRatio` | Connections is where Lambda pipelines break. Replica lag is where read-after-write bugs come from. |
| Business | `RecordsIngested`, `RecordsRejected`, per source | The one nobody adds and everybody needs. Technical metrics tell you the system is up; business metrics tell you it is correct. |

## 10. Aurora and RDS

### What it is

Aurora is AWS's own relational database engine, wire-compatible with MySQL and PostgreSQL. The interesting part is the architecture, and that architecture is the reason for almost every one of its features.

### The architecture, and why it matters

A normal database writes data pages and a write-ahead log to a local disk. Aurora **separates compute from storage completely**. The database instance is only a query engine and a cache; storage is a separate distributed service shared by every instance in the cluster.

- Data is stored as **six copies across three availability zones**, two per zone.
- A write is acknowledged once **four of the six** copies confirm it. Reads need three of six. This quorum means the cluster survives losing an entire availability zone plus one more copy without losing data, and survives losing one whole availability zone without losing availability for writes.
- **Only redo log records cross the network.** Aurora does not send full data pages, does not do a double-write buffer, and does not do full page writes after a checkpoint. The storage layer replays the log to materialise pages itself. This is why Aurora outperforms stock MySQL and PostgreSQL on write-heavy workloads — it is sending far less data over the wire.

Because all instances share one storage layer, the consequences cascade nicely:

- **Replicas are cheap and fast.** Up to 15 read replicas, all reading the same storage, so replication lag is typically in the **low milliseconds** rather than the seconds you get from binlog or WAL shipping. There is no data to copy, only cache invalidation to propagate.
- **Failover is fast**, usually around 30 seconds or less, because a replica does not need to catch up on data — it already shares the storage. It just needs to be promoted.
- **Storage grows automatically** in 10 GB increments up to 128 TB. You never provision disk size or run out of space at 3 in the morning.
- **Backups are continuous** to S3 with no performance impact, and point-in-time recovery is available to the second within the retention window.

### Endpoints, which you must use correctly

| Endpoint | Points at | Use for |
|---|---|---|
| **Cluster (writer) endpoint** | Always the current primary, and follows failover automatically. | All writes. Never hard-code an instance address. |
| **Reader endpoint** | Load-balanced across all replicas, by DNS. | Scale-out reads. Be aware that DNS-based balancing is coarse: a long-lived connection pool can end up unevenly distributed. |
| **Custom endpoint** | A group of instances you define. | Sending analytics or reporting queries to a couple of larger instances so they cannot affect the transactional traffic. |
| **Instance endpoint** | One specific instance. | Diagnostics only. Never in application configuration. |

**The read-after-write trap.** If you write through the cluster endpoint and immediately read through the reader endpoint, you may not see your own write — replication lag is milliseconds, but milliseconds is not zero, and a fast client can beat it. Either read from the writer for the short window after a write, or design the interaction so it does not need to read back immediately. This is a favourite interview follow-up, and the correct answer is not "Aurora replication is fast so it will be fine."

### Aurora Serverless v2

Scales capacity in fine-grained **Aurora Capacity Units**, where each unit is roughly 2 GB of memory with matching CPU and network. It adjusts within seconds while connections stay open, and it can scale down to a small fraction of a unit.

Version 1 had a bad reputation because it paused entirely when idle and resumed slowly, and it scaled by finding a "scaling point" where it could safely swap. Version 2 has neither problem. Its good fit is spiky workloads: a nightly ETL window, a development environment, or a multi-tenant system where each tenant's database is mostly idle. For flat, predictable load, provisioned instances with a savings plan are cheaper.

### The other features worth naming

- **Fast clone** — creates a new cluster from an existing one using copy-on-write on the storage layer. It takes minutes regardless of database size and only bills for pages that diverge. This is how you test a migration against production-sized data without a multi-hour restore.
- **Backtrack** (MySQL-compatible only) — rewinds the cluster in place to a point in time, without restoring to a new cluster. Very fast recovery from "someone ran the wrong UPDATE."
- **Global Database** — a primary region plus up to five read-only secondary regions, replicated through the storage layer with typical lag under one second, and cross-region failover in about a minute. This is disaster recovery and low-latency global reads, not multi-master writes.
- **Performance Insights** — query-level load visualisation showing which statements and which wait events are consuming database time. This is the first place to look when the database is slow, and it is far more useful than CPU utilisation.
- **RDS Proxy** — see below.

### The Lambda plus Aurora problem, and RDS Proxy

This is the classic trap and it comes up in interviews constantly.

Each concurrent Lambda execution environment has its own connection pool, and that pool cannot be shared with any other environment. So 1,000 concurrent Lambdas mean up to 1,000 database connections. Aurora instances have a `max_connections` limit that scales with instance memory, and a small instance may allow only a few hundred. You exhaust it, new connections are refused, and **the failure hits your healthy synchronous traffic as well as the pipeline that caused it**.

It is worse than a simple count problem, because each connection also consumes memory on the database instance, so many idle connections degrade performance even below the hard limit.

The fixes, in the order you should present them:

1. **RDS Proxy.** A managed connection pool sitting between your functions and Aurora. It multiplexes many client connections onto a small number of real database connections, holds the pool through a failover so clients see a much shorter interruption, and supports IAM authentication so functions need no database password at all. This is the standard answer and you should name it first.
2. **Reserved or maximum concurrency** on the pipeline function. This puts a hard ceiling on how many connections that function can ever open. It is free, it takes one line of configuration, and it protects everything else in the account.
3. **Batching.** Process 10 messages per invocation and write them in one statement instead of 10. This cuts both connection count and query count by an order of magnitude.
4. **Move the heavy database work to Fargate.** A long-running container holds one connection pool for its whole life, shared across thousands of requests. For a genuinely write-heavy consumer this is often the right architecture rather than a workaround.

### How Aurora scales

**Reads scale horizontally and easily.** Add replicas, up to 15, and use the reader endpoint. Aurora Auto Scaling can add and remove replicas based on CPU or connection count.

**Writes scale vertically only.** There is exactly one writer instance. You make it bigger; you cannot add a second one (Aurora Multi-Master existed for MySQL 5.6 but is not a general answer). When a single writer is not enough, your options are the real distributed-systems answers: shard by tenant or by another partition key, move high-volume append-only data to DynamoDB or a stream, add caching so fewer writes are needed, or batch writes.

**Storage scales automatically** to 128 TB, in 10 GB steps, with no action from you.

**Connections are the limit you hit first in a serverless architecture** — see the section above.

**What to watch:** `DatabaseConnections` against your maximum, `CPUUtilization` on the writer, `AuroraReplicaLag`, `Deadlocks`, and `BufferCacheHitRatio` (a falling cache hit ratio means your working set no longer fits in memory, and that is your signal to size up before latency degrades).

## 11. How the services combine

Individual service knowledge gets you through the first ten minutes. What separates a strong candidate is being able to explain **why these pieces sit next to each other**. Here are the combinations that come up again and again.

### API Gateway plus Lambda plus Aurora — the standard synchronous API

The default web API. Requests are validated at the gateway, a Lambda handles business logic, Aurora stores the data.

**What to say about it:** protect Aurora with RDS Proxy because Lambda concurrency maps to connections. Use provisioned concurrency on latency-critical routes because Java cold starts are visible to users. Enable caching at the gateway for read-heavy endpoints. If sustained load is high and flat, this is exactly the case where moving to Fargate is cheaper and removes cold starts entirely.

### API Gateway direct to SQS plus Lambda — the burst-tolerant ingestion endpoint

For a write endpoint that receives large spikes, integrate API Gateway **directly with SQS**, with no Lambda at the front. The gateway accepts requests at its own very high rate and puts them straight into a queue; a Lambda drains the queue at whatever pace the backend can take.

**Why this is a good answer:** it removes cold starts from the accept path entirely, it removes any possibility of the write path throttling because of Lambda concurrency, and it turns a traffic spike into a queue backlog rather than a wall of 429 and 500 responses. The trade-off is that the caller now gets a 202 Accepted and does not learn the processing result synchronously, so you need a status endpoint or a notification.

### EventBridge plus SQS plus Lambda — the standard event consumer

**Never point an EventBridge rule directly at a Lambda for a high-volume workload.** Put an SQS queue between them.

What the queue buys you:

- **Buffering.** A spike becomes a backlog instead of a wave of throttled invocations.
- **Independent retry.** Each consumer retries at its own pace with its own dead letter queue. A slow consumer does not affect the others.
- **A place to inspect failures.** A dead letter queue holds the actual failed messages so you can look at them and redrive.
- **Backpressure control.** Maximum concurrency on the event source mapping caps how hard the consumer hits the database.

If you remember one architectural rule from this whole document, make it this one: **bus for routing, queue for buffering.**

### S3 plus EventBridge plus Step Functions plus SQS plus Lambda — the large file pipeline

A partner uploads a large file to S3. The S3 notification goes to EventBridge. A rule starts a Step Functions execution. The workflow uses a Fargate task or Distributed Map to stream and split the file into individual records, publishing each to SQS. Lambda consumers validate and write to Aurora.

**Why each piece is there:** S3 because the file is far too big for any message payload. EventBridge because several teams may want to know a file arrived. Step Functions because the overall job takes longer than 15 minutes and you want to see where it is. Fargate or Distributed Map because splitting a multi-gigabyte file is not a 15-minute job. SQS because a million records need buffering and independent retry. Lambda because per-record work is small, spiky, and parallel.

### Kinesis plus Lambda plus S3 plus Athena — the analytics and change-data-capture path

Events go into a Kinesis stream. One Lambda consumer maintains the operational view. A Firehose delivery stream writes the raw records to S3 in Parquet, partitioned by date. Athena queries the history.

**Why Kinesis rather than SQS:** several independent consumers read the same records, and you can replay the stream when a consumer had a bug. Neither is possible with a queue.

### Step Functions plus Fargate plus Lambda — mixed-duration workflows

A workflow where some steps are short and some are long. Use `ecs:runTask.sync` for the step that takes 40 minutes, and ordinary Lambda tasks for the short steps. Step Functions waits for the container and you do not pay while it waits.

**Why it is a good answer:** it directly addresses the 15-minute Lambda ceiling without abandoning serverless for the whole pipeline, and it shows you pick compute per step rather than per project.

### Lambda plus DynamoDB plus Aurora — idempotency alongside the main store

Aurora holds the business data. A small DynamoDB table with a time-to-live attribute holds processed message identifiers for deduplication. Each consumer does a conditional write to DynamoDB first; if the key already exists, it skips the work.

**Why DynamoDB rather than a table in Aurora:** the deduplication table gets one write per message, which is exactly the high-volume, tiny, key-value access pattern DynamoDB is built for, and it keeps that write load off the database that is already your connection bottleneck. The time-to-live attribute expires old keys automatically with no cleanup job.

### CloudWatch across all of it

Every service above emits metrics automatically. The pieces you have to add yourself are the ones that tell you whether the system is **correct**, not just alive: a count of records in per source, a count of records stored, and a count rejected with reason codes, so you can reconcile "in equals stored plus rejected" at the end of every batch. That reconciliation is what turns "the pipeline ran" into "the pipeline was right," and volunteering it in an interview lands well.

## 12. Scaling, put together in one place

### What scales on its own and what you must tune

| Service | Scales automatically | You must tune | What breaks first |
|---|---|---|---|
| EventBridge | Everything | Nothing on the bus itself | The target being invoked |
| SQS (standard) | Everything | Consumer concurrency, batch size, visibility timeout | Nothing in SQS — the consumer or its database |
| SQS (FIFO) | Within group limits | `MessageGroupId` design, high-throughput mode | Throughput per group |
| Lambda | Environments, up to the account limit | Memory, concurrency limits, batch size | The downstream dependency — usually database connections |
| Step Functions Standard | Executions | Choice of Standard or Express, Distributed Map concurrency | Cost per state transition, and the 25,000-event history limit |
| Kinesis provisioned | Nothing | Shard count, partition key, parallelisation factor | Hot shard, then iterator age |
| Kinesis on-demand | Shard count, with a delay | Partition key | Sudden spikes still throttle |
| API Gateway | Everything | Throttles, usage plans, caching | The backend integration |
| ECS Fargate | Task count, with a policy you write | Target metric and value, cooldowns, minimum and maximum, task size | Task start-up time during a sharp spike |
| S3 | Effectively everything | Key and prefix design | A single hot prefix, or request cost |
| Aurora | Storage, and replicas with auto scaling | Instance size, replica count, connection strategy | Connection count, then single-writer capacity |

### The four scaling patterns worth memorising

**1. Put a queue in front of anything with a hard capacity limit.**
Aurora has a connection limit. A third-party API has a rate limit. A queue converts "too much traffic" into "a longer wait," which is nearly always the better failure mode. This is the single most useful pattern in event-driven design.

**2. Filter as early as possible.**
An EventBridge rule pattern that drops 90 percent of events costs nothing and removes 90 percent of downstream work. Request validation at API Gateway rejects bad input before it reaches compute. Every layer of filtering you push earlier is capacity you did not have to buy.

**3. Cap the fast component to protect the slow one.**
Lambda can scale to thousands of concurrent executions in seconds. Aurora cannot accept thousands of new connections in seconds. Maximum concurrency on the event source mapping is not a limitation you are working around — it is you deliberately matching the fast component to the slow one. Say it that way in an interview.

**4. Batch to trade latency for throughput.**
Ten messages per invocation is one tenth the invocations, one tenth the concurrency, one tenth the connection pressure, and roughly one tenth the cost. The price is latency, because you wait to fill the batch. Almost every asynchronous pipeline should take that trade; almost no synchronous user-facing path should.

### How fast each service can absorb a sudden spike

Ordered from fastest to slowest reaction, because this ordering is what decides where a spike should land:

1. **API Gateway, S3, SQS, EventBridge** — effectively instant. These absorb a spike with no ramp at all.
2. **Lambda** — an initial burst of hundreds to a few thousand concurrent executions, then 500 more every 10 seconds.
3. **Lambda from SQS** — much slower to ramp: five pollers to start, then roughly 60 more concurrent invocations per minute.
4. **Kinesis on-demand** — minutes to double capacity.
5. **ECS Fargate** — 30 to 60 seconds per task, and more for a slow-starting JVM application.
6. **Aurora replicas** — minutes to add.

The design conclusion follows directly: **land the spike on something in group one, and let the slower components drain it.** That is precisely why the API-Gateway-to-SQS and EventBridge-to-SQS patterns exist. Anything that absorbs a spike instantly and holds it is doing the most valuable job in the architecture.

## 13. Rapid-fire questions and answers

**Q: EventBridge or SQS first in your pipeline?**
Bus first, for routing and fan-out. Queue behind each consumer, for buffering and independent retry. The queue is what lets one slow consumer fall behind without dropping events and without affecting the other consumers. If you only have one consumer and no routing needs, you can skip the bus — but you rarely regret having it when the second consumer appears.

**Q: A message keeps failing. Walk me through exactly what happens.**
The consumer throws, so it never deletes the message. After the visibility timeout the message becomes visible again and another consumer receives it. This repeats until the receive count reaches `maxReceiveCount`, at which point SQS moves the message to the dead letter queue. The dead letter queue depth alarm fires and pages someone. We look at the payload, decide whether it is a bug or a genuinely bad record, fix the code or quarantine the record, and then use dead letter queue redrive to send the messages back to the source queue. With `ReportBatchItemFailures` enabled, only the failing message goes round this loop; the other nine in the batch were deleted on the first pass.

**Q: How do you guarantee exactly-once processing?**
You do not, and anyone who says they do is describing at-least-once delivery plus idempotent processing. That combination is "effectively once," which is what people actually mean. Concretely: an idempotency key (the message id, or better, a business key), a conditional write or an upsert so a repeat is a no-op, and a version or timestamp check so an older duplicate cannot overwrite newer data.

**Q: Order matters for a store's inventory updates. How do you handle it?**
Three options, and I would pick based on how much ordering is really needed. A FIFO queue with `MessageGroupId = storeId` gives strict ordering per store with full parallelism across stores. Kinesis with `partitionKey = storeId` gives the same ordering plus replay and multiple consumers, at the cost of managing shards and watching for a hot store. Or avoid ordering entirely: carry a monotonic `version` or `updatedAt` in the message and apply an update only if it is newer than what is stored. That third option is often the best, because it survives duplicates and out-of-order delivery without any infrastructure constraint at all.

**Q: One store is 60 percent of your traffic and its Kinesis shard is saturated. What do you do?**
That is a hot shard, and adding shards will not help, because the hash sends that key to one shard whatever the shard count. Two real fixes. Use a composite partition key like `storeId#bucket` to spread that store across several shards, accepting that I have given up ordering within the store — which I can often recover downstream with a version number. Or narrow the ordering requirement: I usually do not need every event for a store in order, only every event for a given product or order, and that finer key spreads naturally.

**Q: Cost blew up on this pipeline. Where do you look?**
In roughly this order, because this is the order of how often each one is the culprit. CloudWatch log ingestion and log groups with no retention set. NAT gateway data processing charges, which a VPC gateway endpoint for S3 often removes entirely. Lambda gigabyte-seconds, usually from over-provisioned memory or from functions billing while they wait on a slow database call. CloudWatch custom metrics with a high-cardinality dimension somebody added. Step Functions state transitions on a Standard workflow that should have been Express. Kinesis shard-hours for shards provisioned for a peak that no longer happens. S3 request counts on many tiny objects, and abandoned incomplete multipart uploads. EventBridge charges per million events, multiplied by how many rules each event matches.

**Q: One million XML records arrive at once. Design the pipeline.**
Land the raw files in S3 under partitioned prefixes such as `raw/dt=.../source=.../`. S3 notification through EventBridge starts a Step Functions execution. A splitter — either a Fargate task or a Distributed Map, because this will take longer than 15 minutes — streams each file and emits one message per record to SQS, so nothing large ever sits in a message payload. Lambda consumers read the queue in batches of ten, validate each record against the schema, and upsert into Aurora keyed on the natural business identifier so duplicates are harmless. The raw file stays in S3 under a lifecycle rule for audit and reprocessing. Invalid records go to a rejects queue and a rejects prefix in S3 with a reason code, never silently dropped.
The controls I would call out: maximum concurrency on the event source mapping, or RDS Proxy, so the consumers cannot exhaust Aurora's connections; `ReportBatchItemFailures` so one bad record does not force nine good ones to be reprocessed; a dead letter queue with an alarm and a redrive plan; and per-source counters so that at the end I can reconcile records received against records stored plus records rejected. If the numbers do not add up, the pipeline ran but was not correct, and I want to know that automatically rather than from a customer.

**Q: When would you not use Lambda?**
When the work runs longer than 15 minutes. When the traffic is high and flat, because a container is cheaper once you are paying for capacity all the time anyway. When cold starts are visible on a user-facing path and provisioned concurrency would cost more than just running containers. When I need a protocol Lambda does not front well, such as gRPC streaming or long-lived WebSocket connections. And when the workload holds an expensive resource that should be shared, such as a large connection pool or a big in-memory cache, because that is exactly what Lambda's isolation model is worst at.
